# 팩트 카드 — 2026-11-15

## 토픽
클라우드플레어가 에이전트용 브라우저 엔진 **Kitesurf**를 오픈소스로 공개(Apache 2.0).

## 핵심 사실
- 2026-11-12 Cloudflare 개발자 체인지로그 "Kitesurf is now open source" / 블로그 동일 제목. 일부 매체는 11-13으로 보도.
- 저장소: github.com/cloudflare/kitesurf, **Apache 2.0**. 제3자 프로젝트는 각자 라이선스(NOTICE).
- 최초 공개는 2026-08-07(TechCrunch 보도 "Cloudflare launches Kitesurf, a browser built for AI agents"). 관리형 서비스(Browser Run)는 베타이고 **이번 공개 대상이 아님** — 엔진만.
- 전부 **Workers 위에서** 돈다. "browser container 없이" 스크린샷 렌더. 페이지마다 **Dynamic Workers**로 격리 → 자체 배포에는 **Workers Paid 플랜 필요**.
- **내장 인증 없음** — Cloudflare Access 등으로 직접 보호하라고 명시.
- "experimental and under heavy development".

## 구조 (Cloudflare 공식 블로그)
- 세 부분: **Engine**(세션·클라이언트 연결 관리) / **PageScript**(페이지와 JS 실행) / **PageRenderer**(그리기)
- **Blitz**(DioxusLabs) — HTML 파싱·DOM·레이아웃·페인팅
- **Stylo**(Servo) — CSS 파싱·캐스케이드·계산된 스타일
- **Boa** — WASM 안에서 JS 실행. 단 "the last resort", Dynamic Workers에서 JS를 못 돌릴 때만.
- **Linebender** — 텍스트 레이아웃·2D 그래픽 / **Krilla** — PDF 출력
- Rust → WebAssembly 컴파일
- **CDP(Chrome DevTools Protocol) 지원** → Puppeteer·Playwright가 그대로 붙는다. 로컬 `ws://127.0.0.1:8787/devtools/browser`, 관리형은 CDP 엔드포인트에 `?browser=kitesurf`.
- **확장 프로그램 의도적 제외**(보도).

## 숫자 — kitesurf.dev/benchmarks (마지막 실행 2026-11-14 02:40 UTC)
38개 페이지 중간값(각 페이지는 5회 중간값). 비교 대상 3종: Kitesurf / Browser Run(페이지 간 크롬 재사용) / Chrome 콜드 스타트(매번 새 크롬).

| 지표 | 출력 | Kitesurf | Browser Run | Chrome(콜드) |
|---|---|---|---|---|
| 벽시계 | 스크린샷 | **1.79s** | 1.20s | 1.01s |
| 벽시계 | HTML | 1.37s | 1.10s | 894ms |
| CPU 시간 | 스크린샷 | **387ms** | 1.67s | 767ms |
| CPU 시간 | HTML | 446ms | 1.59s | 637ms |
| 메모리 | 스크린샷 | **50 MiB** | 400 MiB | 329 MiB |
| 메모리 | HTML | 29 MiB | 398 MiB | 316 MiB |

페이지별 벽시계(중간값) 발췌:
- Hacker News: Kitesurf **609ms** vs Browser Run 920ms vs Chrome콜드 1.51s  ← 역전
- fingerprint 홈: 971ms vs 1.28s vs 1.48s ← 역전
- El Mundo: **14.0s** vs 4.20s vs 2.74s  ← 참패
- The Guardian: 9.79s vs 2.08s vs 1.39s
- Cloudflare 자사 블로그: 4.12s vs 1.23s vs 983ms ← 자기 사이트에서 짐
- TodoMVC(React/Vue/Angular/Preact): 대체로 비슷
- 렌더 실패: relic 3페이지는 Browser Run이 실패, trysansa 1페이지는 Kitesurf 실패

**페이지 자체 명시 주의사항(반드시 반영):**
- Chrome 콜드 스타트 벽시계는 **실행(launch) 시간을 제외**한 값이다.
- Kitesurf 타이머는 응답 전체 읽기를 포함한다.
- 클라이언트→Cloudflare 네트워크 시간은 어느 쪽에도 미포함.
- CPU 시간은 프로세서 시간(경과 시간 아님).
- 메모리는 캡처 시점 절대치이며, Browser Run 수치는 **이전 페이지에서 남은 메모리 포함** 가능.
- 페이지별 CPU·메모리는 공개돼 있지 않고 총괄 수치만 있다.

## 숫자 — kitesurf.dev/wpt (마지막 실행 2026-11-13 16:24 UTC)
- 서브테스트 **1,517,208 / 1,543,968 = 98.3%**
- 테스트 **파일 9,093 / 11,764 = 77.3%**
- 건너뜀 56,854 파일. 이전 실행 대비 ±0.
- 유일한 비교 기준은 Chrome 154(건너뛴 서브테스트 수 산정용). 크롬 통과율은 이 페이지에 없음 → **"크롬보다 몇 % 낮다"고 쓰지 말 것.**

## 바꾸는 것
에이전트 브라우징을 운영할 때 **재는 숫자가 바뀐다.** 지금까지는 페이지 로드 시간(벽시계)을 쟀지만, 동시 실행 수를 결정하는 것은 **페이지당 메모리와 CPU 시간**이다. 같은 머신에서 크롬은 페이지당 ~329 MiB, Kitesurf는 ~50 MiB → 동시 처리 가능 페이지 수가 한 자릿수 배 차이. 그리고 CDP 호환이라 **기존 Puppeteer 스크립트로 자기 페이지 목록을 돌려 직접 재 볼 수 있다**(엔드포인트만 교체).
둘째, 에이전트 브라우저가 더 이상 Chromium이 아니게 되면 **핑거프린트 기반 봇 탐지의 전제가 무너진다** — 신호가 "숨긴 봇"이 아니라 "다른 브라우저"를 가리키게 된다.

## 설명할 메커니즘
**벽시계 시간과 CPU 시간·메모리는 서로 다른 자원이고, 사람용 브라우저는 앞의 것을, 에이전트는 뒤의 것을 최적화해야 한다.**
1. 사람용 브라우저는 "한 사람이 한 페이지를 볼 때 첫 픽셀까지 얼마나 빠른가"를 줄이려고 CPU·메모리를 아끼지 않는다 — 투기적 파싱, JIT, GPU 합성, 탭별 프로세스 격리, 캐시, 확장 프로그램.
2. 에이전트는 화면을 보지 않는다. DOM 텍스트, 가끔 스크린샷. 대신 **동시에 수백 페이지**를 연다.
3. 그러면 청구서가 벽시계가 아니라 **CPU-초와 RSS**로 매겨진다 → 느린데 싼 쪽이 이긴다.
4. 보너스 메커니즘: **WPT 서브테스트 98.3% vs 파일 77.3%의 간극** — 서브테스트는 잘게 쪼갠 개별 검증이고 파일은 "그 파일 안의 모든 서브테스트가 통과했는가". 한 파일에 하나만 틀려도 파일은 실패. 실무적 의미 = "대부분의 기능은 되는데, 어떤 페이지는 통째로 안 된다". 벤치마크 표의 렌더 실패 1건이 그 증거.

## 출처 바깥의 사고 (가정 — 예측 아님을 명시할 것)
클라우드플레어는 봇을 막는 쪽(Verified Bots 2025-07, signed agents 2025-08, Web Bot Auth 드래프트 참여)과 에이전트 브라우저를 만드는 쪽을 동시에 한다. Kitesurf가 널리 쓰이면 "진짜 브라우저인가"를 묻는 탐지는 무력해지고, 판별 축이 "무슨 브라우저냐"에서 "누구냐(서명된 신원)"로 옮겨갈 수밖에 없다. 근거: 확장 프로그램 의도적 제외, GPU 합성 경로 부재, 벤치마크 목록에 fingerprint 페이지 포함. ※ 2026-10-13 편(에이전트가 자신을 에이전트라고 밝히는 표준)을 가볍게 재호출.
