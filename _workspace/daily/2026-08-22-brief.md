# 2026-08-22 데일리 포스트 팩트 카드

## 선정 토픽
바이낸스가 AI 에이전트에게 실거래 권한을 여는 Agent OS·MCP 서버 출시 (현지 2026-08-20)

## 왜 이 토픽인가
- 신선도: 현지 8/20 발표, 8/21까지 후속 보도. 24~48시간 기준 충족.
- 엔지니어 접점: MCP 서버 권한(scope) 설계라는 실무 주제가 '남의 돈'과 처음으로 정면 충돌한 사례.
- 논쟁 각도: 거래소가 만든 안전장치는 전부 '경계선'인데, 손실에는 한도가 없고 거래소는 에이전트의 판단 근거를 볼 수 없다.
- 한국 접점: 다올투자증권이 이미 7/27 'MCP 트레이딩' 사전예약을 열었고 8월 오픈 예정. 금융위는 AI 에이전트 대비 망분리·데이터 규제 정비 중.
- 중복 확인: topics-written에 바이낸스·거래소 에이전트 항목 없음. 08-18 스트라이프/오픈라우터는 '결제 레일' 각도로 다름. 07-15 MCP는 '프로토콜 표준 전쟁' 각도로 다름.

## 핵심 팩트 (교차 확인)
1. 발표일: 현지 2026-08-20. Binance Agent OS + Binance MCP Server 동시 출시.
2. 구성 요소 5개: Binance APIs(거래·시세·지갑·온체인), Wallet Agentic Hub, Binance x402(HTTP 402 기반 에이전트 결제), Skill Hub, MCP Server.
3. 지원 클라이언트: ChatGPT, Codex(OpenAI), Claude·Claude Code(Anthropic), Cursor, VS Code.
4. 권한 구조
   - 시세 등 공개 데이터: 인증 불필요(읽기 전용)
   - 거래: 현물, 마진, Convert, USDⓈ-M / COIN-M 선물
   - 계좌: 잔고 조회, 내부 이체
   - **출금: 외부 주소로의 출금 불가(기본 차단). 메인 계좌 → 에이전틱 서브계좌 이동도 에이전트가 못 함(사용자가 직접 입금)**
5. 한도 (Agentic Wallet 기준, 바이낸스가 정한 일일 한도)
   - 일반 스왑: 하루 5만 달러
   - DeFi 거래: 하루 10만 달러(기본값)
   - x402 결제: 하루 20달러
   - **현물·선물 거래 서브계좌: 별도 손실 한도 없음 — 사용자가 서브계좌에 넣은 금액이 곧 한도**
6. 승인 모드: 주문마다 사용자 승인을 받게 할 수도, 권한 설정 후 자율 거래를 허용할 수도 있음. 권한은 언제든 회수 가능.
7. 발언 (제프 리 / Jeff Li, 바이낸스 제품 부사장, TechCrunch 2026-08-20)
   - "Instead of total freedom, we put the power in users' hands to give them the granular access control of what they can do through the agent."
   - "We really cannot see the reasoning of what the user's action is."
8. TechCrunch가 짚은 위험: 바이낸스는 에이전트의 판단 근거를 볼 수 없고 조작 여부도 탐지 못함, 거래 손실 한도 없음, 감시 책임이 사용자에게, 프롬프트 인젝션 취약성 인정.
9. 경쟁사 타임라인: OKX 2025년 초 MCP 툴킷 / 크라켄 2026-03 오픈소스 CLI(소비자 어시스턴트는 승인 필요) / 코인베이스 2026-06 Agents 플랫폼 / 바이낸스 2026-08 서브계좌 샌드박스형

## 한국 팩트
- 다올투자증권: 2026-07-27 'MCP 트레이딩' 사전예약 접수 개시. ChatGPT·Claude 등 생성형 AI 대화창에서 국내주식 시세·보유종목·계좌잔고·주문가능금액 조회부터 주문 요청까지. 2026년 8월 오픈 예정(사전예약 고객 우선). 기사에 안전장치·권한 관련 언급 없음. 회사 관계자 발언은 실명 미표기 — 본문에서 인물 인용하지 않는다.
- 금융위원회: AI 에이전트 시대 대비해 망분리 추가 완화, AI 학습용 개인신용정보 동의 제도·가명처리·결합·재사용 규제 정비 추진 (이데일리 마켓인).

## 평론 각도
MCP 권한 설계에서 우리가 다듬는 것은 scope 목록인데, 실제 blast radius를 정하는 것은 scope가 아니라 그 scope가 닿을 수 있는 자산의 크기다. 출금 차단은 '자산이 밖으로 나가는 것'을 막았을 뿐 '자산이 사라지는 것'은 막지 못한다 — 거래는 원래 돈을 잃을 수 있는 행위이기 때문. 게다가 클라이언트가 LLM이라 시장 데이터라는 외부 텍스트가 곧 명령이 될 수 있고(프롬프트 인젝션), 거래소는 판단 근거를 못 본다. 결국 안전장치의 실체는 권한 목록이 아니라 '서브계좌에 얼마를 넣었는가'다.
