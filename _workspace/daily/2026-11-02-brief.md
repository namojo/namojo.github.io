## 배경 메커니즘
- Microsoft Marketplace 퍼블리셔 약관 3.a: 마켓플레이스는 Visual Studio 제품군(Microsoft가 제공하는 VS Code 포함) 외의 제품을 지원하는 데 쓸 수 없음 → VS Code 포크(Cursor, Windsurf, VSCodium, Gitpod, Coder)는 공식 마켓플레이스를 못 쓴다.
- 대체재: Eclipse Foundation의 Open VSX. 다만 Cursor는 자체 마켓플레이스도 운영.
- 규모 비교(2023년 시점 보도): VS Marketplace 48,000+ 확장 / Open VSX 약 3,000.
- 전례: 2025년 Koi Security가 Open VSX 자동 게시 파이프라인에서 `OVSX_PAT`(수퍼관리자급 토큰)가 매일 도는 GitHub Actions 잡의 `npm install` 빌드 스크립트에 노출되는 결함 발견. 2025-05-04 Eclipse 통보, 2025-06-25 수정 배포. Koi는 800만+ 개발자 영향 가능성 주장. Eclipse는 기존 확장·관리 기능 영향 없고 실제 악용 증거 없다고 밝힘.

## 바꾸는 것
- 편집기 확장은 "설치 즉시·편집기 실행 때마다" 샌드박스 없이 돌고 자동 업데이트가 기본값이다. 같은 이름·같은 퍼블리셔라도 **어느 마켓플레이스에서 왔는지에 따라 신뢰 사슬이 다르다** — VS Code에서 믿던 배지가 포크에서는 다른 창고의 배지다.
- 독자가 내일 할 수 있는 일: 10/29에 Claude Code 확장 2.1.312/2.1.313을 받았는지 확인, `~/.ssh/authorized_keys`에서 `svc-telemetry` 검색, LaunchAgent/예약 작업/crontab 점검, 해당 머신에서 닿던 자격증명 회전. **확장 삭제만으로는 정리되지 않는다** — 페이로드가 쓴 것들이 확장 폴더 바깥에 있다.
- 조직 차원: 락파일·의존성 쿨다운·패키지 방화벽은 전부 저장소 안쪽을 본다. 편집기 확장은 그 바깥이라 SBOM에도 안 잡힌다.

## 설명할 메커니즘
1. VS Code 포크가 왜 자기 마켓플레이스를 따로 갖는가 (약관 3.a → Open VSX / 자체 레지스트리). 확장의 신원은 이름이 아니라 그 이름을 누가 관리하는 창고에 달려 있다.
2. 확장과 패키지의 차이: npm 패키지는 빌드·실행 시점에 돌지만 확장은 편집기가 켜지는 순간 activate()가 돈다. 샌드박스 없음, 편집기와 동일 권한, 자동 업데이트 기본값.
3. 악성 로더가 extension.js 선두에 붙고 나머지는 그대로 → 사용자 화면에 달라지는 게 없다.
4. 삭제가 정리가 아닌 이유: 지속성 산출물이 확장 디렉터리 바깥(authorized_keys, LaunchAgent, 예약 작업, crontab)에 있다.

## 평론 각도
"확장 하나가 뚫렸다"가 아니라 "편집기 플러그인 층은 우리가 세운 공급망 방어선 바깥에 있다". 다만 사정거리는 긋는다 — 대부분 호스트에서 SSH 활성화는 실패했고, 침해 경로는 아직 공개되지 않았다.
