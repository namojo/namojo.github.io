## 동작 메커니즘
### (1) `.pth` 시작 훅 — 임포트하지 않아도 실행
- 1.26.1: `agent_framework_meta.pth` + `agent_framework_meta/_telemetry.py`, `__init__.py` 변조
- 1.26.2: `af_runtime_diag.pth` + `af_runtime_diag.py`, `__init__.py`는 원본 복구
- `.pth` 내용은 한 줄: `import agent_framework_meta` / `import af_runtime_diag`
- 파이썬 표준 라이브러리 `site` 모듈이 인터프리터 시작 시 site-packages의 `.pth`를 전부 읽고,
  `import `로 시작하는 줄은 그대로 실행한다 (원래 용도는 sys.path 추가)
- → 사용자가 패키지를 한 번도 import 하지 않아도, 설치만 되어 있으면 python 실행 순간 코드가 돈다
- Unix: fork + `setsid()`로 자식 프로세스 분리 / Windows: 백그라운드 스레드
- `_AF_TEL` 환경변수로 프로세스 트리당 1회만 실행

### (2) 수집 대상
- 환경변수: TOKEN·SECRET·PASSWORD·KEY·AZURE·AWS·GITHUB 등 31~35개 부분문자열 매칭
- 자격증명 파일 최대 80개 (1.26.1은 60개): Azure CLI 토큰 캐시, `.npmrc`, `.netrc`,
  `.git-credentials`, Docker `config.json` 등
- 다른 프로세스의 환경: `/proc/*/environ` 앞 300개 프로세스

### (3) OIDC 토큰 신규 발급 (핵심)
- Azure DevOps: `SYSTEM_ACCESSTOKEN` + `SYSTEM_OIDCREQUESTURI` → `api://AzureADTokenExchange`
  스코프 요청 (`serviceConnectionId`를 생략해 실제 연합 자격증명과 매칭될지는 불확실 — Elastic)
- Azure 관리 ID: `IDENTITY_ENDPOINT`/`MSI_ENDPOINT`, 없으면 IMDS `169.254.169.254`.
  12개 리소스에 토큰 요청 (Azure DevOps `499b84ac-...` 포함). `IDENTITY_HEADER`도 수집
- GitHub Actions (1.26.2만): `ACTIONS_ID_TOKEN_REQUEST_URL` +
  `ACTIONS_ID_TOKEN_REQUEST_TOKEN` 또는 `ACTIONS_RUNTIME_TOKEN`
  → audience `api://AzureADTokenExchange`, `https://management.azure.com/`
- ⚠ 토큰 발급 "시도"이며 실제 발급·성공 여부는 확인되지 않음 (StepSecurity)

### (4) 유출
- `webhook[.]site/d381fd80-ec62-42ad-8f5c-d1b15103c9bb?t=telemetry`
- JSON → zlib 압축 → Base64 → POST 1회, `application/octet-stream`
- User-Agent: `af-runtime-diagnostics/1` (1.26.1) / `runtime-diagnostics/1` (1.26.2)
- 도메인 접속 기록만으로 실제 전송을 단정할 수 없음 (StepSecurity)

## 바꾸는 것
독자가 내일 회의에서 쓸 문장:
- "우리 CI 러너 안에서는 아무 코드나 환경변수만 읽으면 클라우드 토큰을 새로 발급받을 수 있습니다."
- "장기 비밀을 없애고 OIDC로 옮긴 건 맞는데, 발급 창구가 러너 안에 열려 있는 건 그대로입니다."
- 실행 항목: (a) site-packages에서 `agent_framework_meta.pth`·`af_runtime_diag.pth` 검색
  (b) `agent-framework==1.26.0` 해시 고정 (c) 영향받은 러너의 모든 비밀 회전
  (d) GitHub OIDC 권한·Azure 연합 자격증명·DevOps 서비스 연결·관리 ID 역할 할당 감사
  (e) 러너 이그레스에서 webhook.site 차단, 신규 배포 버전 채택에 지연 두기
- ⚠ 핵심: 짧은 수명 토큰은 **회수할 수 없다.** 신뢰 관계를 끊어도 이미 발급된 토큰은 만료까지 산다.
  비밀번호는 바꾸면 끝이지만 이쪽은 기다리는 수밖에 없다.

## 설명할 메커니즘
독자가 오늘 처음 알게 되는 원리 하나:
**`.pth` 파일은 파이썬 인터프리터가 시작할 때마다 읽히고, `import`로 시작하는 줄은 실행된다.**
"설치는 했지만 import 하지 않았으니 괜찮다"는 안전지대가 애초에 존재하지 않는다.
비유: 집에 들인 가구인데, 문을 열 때마다 저절로 켜지는 스위치가 달려 있다.
(원래 용도는 경로 등록 — `.pth`의 p는 path다. 거기에 실행 기능이 딸려 온 것.)

두 번째 축: 비밀을 없앴더니 **비밀을 찍어내는 창구**가 남았다.
`ACTIONS_ID_TOKEN_REQUEST_URL`은 비밀이 아니라 주소다. 그래서 아무도 그걸 비밀 관리 대상으로
보지 않았다. 그런데 같은 러너에서 도는 코드에게는 그 주소 하나면 충분하다.

## 출처 바깥의 사고 (가정, 예측 아님)
이번 공격이 6분 만에 잡힌 건 **밖으로 나갔기 때문**이다. webhook.site로 한 번 POST를 쐈고,
그 도메인과 User-Agent가 지문이 됐다. 그런데 요청한 audience 중 하나가
`https://management.azure.com/`이었다. 그 토큰은 들고 나가서 쓰는 게 아니라
**받은 자리에서 쓰는** 용도다. 러너 안에서 토큰을 받아 그대로 클라우드 API를 호출하면
외부로 나가는 통신이 한 번도 없고, 그 호출은 전부 허용된 주소로 간다.
근거: 요청 audience 구성 + 러너의 이그레스 통제는 보통 "허용 목록"이고 클라우드 엔드포인트는
그 목록 안에 있다. 실제로 그런 변종이 있다는 말은 아니다.
