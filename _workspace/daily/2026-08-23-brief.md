# 2026-08-23 데일리 포스트 팩트 카드

## 선정 토픽
리니어(Linear)가 공개한 자사 제품 데이터 리포트 — **AI가 리니어에 만들어지는 것의 "절반 가까이"를 작성하게 됐지만, 제품 개발에 드는 총 시간은 줄지 않고 늘었다**

## 선정 사유
- 엔지니어 독자 직결: AI 코딩 에이전트 도입 효과를 벤더 마케팅이 아니라 **실사용 제품 텔레메트리**로 측정한 드문 자료(저자 스타일: 벤더 스펙보다 실사용 검증).
- 저자 시그니처와 정합: "숫자는 틀리지 않았지만 전부는 아니었다" — '절반'은 대체된 절반이 아니라 **더해진 절반**이다.
- 저자 논지 3·2와 직결: 실행은 AI가 삼켰는데 '무엇을 만들지 정하는' 시간은 한 칸도 안 움직였다 → "질문하는 인간만이 살아남는다".
- 최근 발행분과 중복 없음(08-22 바이낸스 권한, 08-21 FDA 근거 공백, 08-20 H200 수입 허가).

## 1차 출처 (Linear, `linear.app/data`)
- 리포트 표기: **EDITION 01 — TIM QI (2026)**. 제목 "How teams build / AI usage patterns in software teams".
- 데이터 범위: **2024년 6월 ~ 2026년 8월**, **유료 워크스페이스만** 집계(무료 제외).
- 표본: 도입률 분석 `N = 127,000 유료 사용자`(2026년 1월과 6월에 모두 활성). PR 분석 `N = 47,900 유료 워크스페이스`(2026년 6월).
- **AI 작성 비중:** "Two years ago, fewer than one issue in a thousand was created by AI. Teams now use AI to write **just under half of everything created**" — 2년 전 1,000건 중 1건 미만 → 2026년 8월 현재 절반 가까이. 에이전트·MCP 클라이언트가 만든 이슈가 **주당 약 2,500건**(사람+기존 연동이 만든 것도 대략 같은 규모).
- **PR 물량:** 워크스페이스당 개설 PR이 2024년 6월 대비 **111% 증가**.
- **코딩 에이전트 연결 팀:** 주당 PR **21건 → 65건**(약 3배). 미연결 팀은 **주당 8~10건**으로 거의 정체.
- **시간(핵심 인용):** "Time spent on existing tasks in Linear held while AI usage appeared as a **new layer of work**, meaning the overall time spent on product development is **going up rather than down**."
- **계획 영역(핵심 인용):** "Time spent on customer requests, docs, and projects **held steady** in a year when nearly everything else in this report moved up."
- **총평(핵심 인용):** "AI has so far changed **how teams execute** far more than **how they decide what to build**."
- 도입률 부수 수치: 2026년 1~6월 AI 기능 활성 사용자 비중이 전 직군에서 2배 이상. Product 12% → 34%(+22p), GTM 5% → 18%(+13p). 201명 이상 기업 CEO 9% → 36%(+27p). 기업 규모 무관하게 약 8~9% → 23~27%. 비엔지니어의 코드 기여 증가(PM +7p → 10%, 디자이너 +7p → 8%).
- 엔지니어링의 create·triage 합산 시간 변화는 `+5m`.
- 출처 URL: https://linear.app/data

## 보강 출처 — 인식과 실제의 간극 (METR RCT)
- METR, "Measuring the Impact of Early-2025 AI on Experienced Open-Source Developer Productivity", **2025년 7월 10일** 공개.
- 설계: 숙련 오픈소스 개발자 **16명**, 자기 저장소의 실제 작업 **246건**을 무작위로 AI 허용/금지에 배정(도구는 주로 Cursor Pro + Claude 3.5/3.7). 대상 저장소 평균 2만 2,000+ 스타, 100만+ 줄.
- 결과: 사전 예상 **+24% 빨라질 것** → 작업 후 자기 평가 **+20% 빨라졌다** → 실측 **19% 느려졌다**.
- 출처 URL: https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/
- ⚠ 주의: 이 "체감 +20% / 실제 −19%" 수치를 **LinearB의 2026년 800만 PR 벤치마크**로 잘못 붙여 놓은 2차 블로그가 다수 있다(리니어 ≠ LinearB). 반드시 METR로 귀속한다.

## 역사 앵커 (도입부용)
- **진 암달(Gene Amdahl)** — IBM System/360의 수석 아키텍트. 1967년 AFIPS 춘계 합동 컴퓨터 학회 논문 "Validity of the single processor approach to achieving large scale computing capabilities"에서 이른바 **암달의 법칙**을 제시. 요지: 프로그램에서 병렬화할 수 없는 부분이 남아 있으면, 프로세서를 무한히 늘려도 전체 속도 향상에는 상한이 있다. 이후 암달 코퍼레이션 창업.
- 도입 템플릿: **D(인물 일화형) 변형** — 인물 이름으로 먼저 들어가고 연도는 뒤에서. 최근 3편(08-20 통찰형, 08-21 숫자형, 08-22 일상 관찰형)은 모두 연도로 시작하지 않았고, 템플릿 A 연속 사용도 없음.

## 평론 각도
1. **'절반'의 재해석:** 절반은 사람이 하던 일의 절반을 AI가 가져간 것이 아니다. 리니어 문장 그대로 "새로운 층(new layer)"이 얹힌 것이고, 기존 작업 시간은 그대로 남았다. 그래서 총합이 늘었다.
2. **암달의 법칙이 조직에도 적용된다:** AI가 가속한 구간(코드·이슈 작성)이 전체 개발 시간의 일부라면, 그 구간을 무한히 빠르게 해도 전체 단축폭에는 상한이 있다. 리니어 데이터에서 유일하게 움직이지 않은 칸이 고객 요청·문서·프로젝트, 즉 **무엇을 만들지 정하는 시간**이다 — 그게 직렬 구간이다.
3. **인식과 실제의 간극:** PR 21 → 65는 눈에 보이고 청구서에도 찍히지만, 늘어난 총 시간은 아무 대시보드에도 안 찍힌다. METR RCT가 보여준 것도 같은 방향(체감 +20%, 실측 −19%).
4. **한국 접점 / 마무리:** 국내 조직 다수가 AI 도구 도입을 산출량 지표(도입률, PR 수, 토큰 사용량)로 관리한다. 그런데 리니어 데이터가 말하는 건 산출량은 이미 두 배가 됐고 안 움직인 건 판단이라는 것. 재는 지표를 산출량에 두면 늘어난 총 시간은 계속 보이지 않는다. 마무리 유형 6(열린 권유형).
- 이전 글 자기 참조(가볍게): 토큰 소비량이 성과가 아니라는 얘기를 예전에 다룬 적 있음(2026-07-04 tokenmaxxing 편) — 날짜·매체 명시 없이 "예전에 ~ 다룬 적이 있는데요"로.

## 균형 (반드시 본문에 반영)
- 리니어 데이터는 **자사 제품 텔레메트리**이고 **유료 워크스페이스 한정**이다. 리니어를 쓰는 조직이 업계 전체를 대표하지 않고, 리니어 밖(코드 저장소, CI, 배포)에서 일어난 절약은 이 데이터에 안 잡힌다.
- 리포트가 다루지 않은 것: AI가 만든 이슈의 완료·폐기율, 코드 리뷰 소요 시간, PR 품질. 즉 "늘어난 PR이 나쁜 PR이었다"는 결론은 이 데이터로 말할 수 없다.
- 총 시간 증가는 도입 초기 학습 비용일 수 있다. 2년치 추세지만 에이전트 연결은 최근 구간에 집중돼 있다.
- METR은 표본 16명·오픈소스 성숙 저장소라는 좁은 설계이고 2025년 초 모델 기준이다. 지금 모델에 그대로 대입할 수 없다.
- 리포트 공개 시점은 페이지에 명시돼 있지 않다("EDITION 01", 2026). 본문에서 특정 발표일을 단정하지 않는다.
