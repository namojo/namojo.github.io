# 팩트 카드 — 2026-11-25

## 토픽
OpenJDK Base64 디코더 인트린식 힙 오버플로 (CVE-2026-114938, "Java4Shell")
— 같은 JDK·같은 바이트코드인데 **CPU가 AVX-512 VBMI를 지원하는지에 따라 취약 여부가 갈린다.**

## 날짜
- 2026-11-17: Calif(calif.io)가 공개. Oracle이 같은 날 11월 Critical Patch Update로 수정 배포. OpenJDK 권고도 같은 날. CISA가 같은 날 즉시 패치 권고 알림 발표(KEV 등재는 아님).
- 2026-11-18: AWS 보안 공지(2026-189-AWS) 최초 게시(19:00 PST).
- 2026-11-23: AWS 공지 최종 갱신(13:00 PST) — 서비스별 패치가 아직 진행 중.
- 2026-11-22 기준 CISA KEV 미등재, 확인된 실제 악용 사례 없음.

## 주체
- 발견·보고: Calif (calif.io). 자체 PoC 공개, 제품별 익스플로잇 체인은 비공개.
- 수정: Oracle / OpenJDK 프로젝트, 그리고 이를 기반으로 하는 배포판 전부
  (Amazon Corretto, Eclipse Temurin, Microsoft Build of OpenJDK, Red Hat, Oracle Java SE 등).

## 핵심 숫자·사실

### 영향 범위
- **JDK 버전:** OpenJDK **17.0.6 이상**, 그리고 21·25·27 라인. 17.0.0~17.0.5는 미해당.
  Java 8(일반 OpenJDK)·11은 해당 디코더 자체가 없어 미해당.
  (단 Oracle 목록에는 Java 8 Enterprise Performance Pack 8u511b33-perf 포함)
- **CPU:** x86-64 중 CPUID leaf 7의 네 기능을 **모두** 보고하는 것만 해당 —
  bmi2(EBX bit 8), avx512f(EBX bit 16), avx512bw(EBX bit 30), avx512vbmi(ECX bit 1).
  - 해당: Intel Xeon Ice Lake / Sapphire Rapids / Emerald Rapids / Granite Rapids, AMD Zen 4 이후(EPYC·Ryzen)
  - 미해당: ARM64(AWS Graviton, Apple 실리콘 네이티브 런타임 등)
  - ⚠ **AVX-512가 있다고 다 해당하는 것이 아니다** — Skylake 세대 Xeon Platinum 8168은 AVX-512는 있으나 avx512vbmi가 없어 미해당.
- **API:** `Base64.getDecoder()`·`Base64.getUrlDecoder()`가 해당. `Base64.getMimeDecoder()`는 그 경로를 타지 않음(17.0.6 빌드 기준 확인).
- **기본 설치로 영향받는다고 보고된 제품:** Keycloak, Atlassian Jira, Atlassian Confluence, JFrog Artifactory, Jenkins, PingFederate.

### 임시 완화책
- `-XX:-UseBASE64Intrinsics` — 해당 인트린식만 끈다(좁은 선택지). AWS는 "즉시 업데이트가 불가능한 경우에만" 권고.
- `-XX:UseAVX=2` — AVX-512 자체를 끈다. x86-64 전용(ARM JVM은 이 플래그로 기동 실패). 다른 AVX-512 연산에도 영향.
- AWS WAF: KnownBadInputs 관리형 룰 그룹 1.28로 고정 + Java4Shell 룰을 Count→Block. **부분 커버리지일 뿐**이고 패치가 완전한 해결.
- CISA: 패치 불가 시 애플리케이션 경계에서 Base64 입력 검증·제한, 미인증 접근 제한.

### 확인 방법
```
# 1) CPU가 네 기능을 다 보고하는가 (네 줄이 다 나와야 해당)
grep -m1 '^flags' /proc/cpuinfo | tr ' ' '\n' | grep -E '^(avx512f|avx512bw|avx512vbmi|bmi2)$'
# ⚠ 오래된 커널은 실제로 있는 기능을 누락 보고할 수 있음 → cpuid 패키지로 직접 읽어 교차 확인

# 2) JVM이 실제로 무엇을 골랐는가 (운영과 같은 바이너리·같은 옵션으로)
java -XX:+PrintFlagsFinal -version | grep -E ' (UseAVX|UseBASE64Intrinsics) '
# UseAVX = 3 이면 AVX-512 경로. UseBASE64Intrinsics=true 만으로는 노출 확정이 아님
```
- VM은 하이퍼바이저가 노출하는 CPU 모델에 달렸다. 패스스루 구성에서는 네 기능이 모두 보였다(⚠ 출처 정정: Calif 아님 — Eclypsium 랩).
- **VM이 신형 호스트로 라이브 마이그레이션되거나 클라우드 인스턴스 타입이 바뀌면 취약 집합으로 들어올 수 있다.** (⚠ 출처 정정 2026-11-25 팩트체크: Calif 아님 — Eclypsium / Security Boulevard 기고, 필자 Chris Garland)

## 바꾸는 것
독자가 내일 회의에서 쓸 문장:
"JDK 버전만 보면 안 됩니다. **운영 인스턴스의 CPU 세대**를 같이 봐야 하고, 오토스케일링 그룹이
인스턴스 패밀리를 섞어 쓰면 **같은 서비스인데 노드마다 취약 여부가 다릅니다.**"
구체적으로 바뀌는 일:
1. 취약 자산 목록의 키가 "소프트웨어 버전"에서 "버전 × CPU 세대 × 하이퍼바이저가 노출한 모델"로 늘어난다.
2. 스테이징(구형 Xeon·ARM 맥북)에서 재현되지 않는다. 테스트로 못 잡는다.
3. 미인증 경계에서 Base64를 푸는 지점(JWT, Basic 인증 헤더, 쿠키, 멀티파트)이 곧 공격면.
4. 패치 불가 구간에는 플래그 두 개 중 **좁은 쪽**(`-XX:-UseBASE64Intrinsics`)을 쓰고 `PrintFlagsFinal`로 적용을 확인한다.

## 설명할 메커니즘
**"자바 소스에 적힌 코드가 실제로 도는 코드가 아니다" — HotSpot 인트린식 치환.**

1. `Base64.getDecoder().decode(byte[])`는 출력 배열 크기를 **정확히** 계산해 할당한다. 할당은 버그가 아니다.
2. 호출 사슬 아래쪽의 `decodeBlock()`은 인트린식 후보다. JIT(C2)가 뜨거운 경로를 컴파일할 때,
   JVM이 기동 시 CPUID로 읽어 둔 기능 집합을 보고 **자바 메서드 본문을 손으로 쓴 AVX-512 어셈블리 스텁으로 갈아 끼운다.**
   → 같은 .class, 같은 JDK, 다른 CPU = **다른 기계어**.
3. 스텁은 입력 64바이트 → 출력 48바이트씩 처리하고, 64바이트 미만으로 남은 꼬리는 별도 핸들러가 맡는다.
4. 꼬리 핸들러가 "몇 바이트 쓸 것인가"를 `(길이 / 4) * 3`으로 계산한다.
   꼬리가 `=` 한 바이트뿐이면 → 0, 거기서 패딩 몫 1을 빼면 → **-1**. 음수 검사가 없다.
   (예: `A` 128개 + `=` 하나 → 128자는 96바이트로 정상 디코드되고, 꼬리에 `=`만 남는다. 할당된 출력 배열은 98바이트.)
5. 쓸 바이트 수로 저장 마스크를 만든다. 전부 1인 64비트에서 하위 N비트만 남기는 식인데,
   N을 하위 1바이트에서 읽기 때문에 -1이면 255 → 64비트 폭을 넘어 **마스크가 전부 1로 남는다**
   → 마스크드 스토어가 **64바이트 벡터를 통째로 기록** → 98바이트 배열 뒤로 **62바이트 초과 기록**.
6. 디코더는 결국 `IllegalArgumentException`을 던지지만 **쓰기는 이미 끝난 뒤다.** 자바 API는 실패 시 출력이 부분적으로 쓰인 상태를 허용하므로, 예외를 잡아도 훼손은 남는다.
   ⚠ 출처 정정 2026-11-25 팩트체크: 이웃 배열 헤더 훼손 + GC 중 JVM 크래시는 **Calif가 아니라 Datadog Security Labs 자체 시험** 결과다. Calif 공개문에는 GC 크래시 서술이 없다("Incorrect placement could cause the JVM to crash, but in many instances, we can simply try again"까지만).
7. 덮어쓰는 값은 공격자가 완전히 고르지는 못한다(꼬리 핸들러가 남는 입력 자리를 `a`로 채워 `69 a6 9a` 반복 패턴이 섞인다). **DoS가 더 쉽게 달성되는 영향**이라는 평가는 ⚠ **Calif가 아니라 Datadog**(및 VulnCheck 케이틀린 콘던)의 것이다. **Calif 본인은 반대로 더 강하게 썼다** — "With careful exploitation, the corruption can reveal sensitive memory, as Heartbleed did, or lead to remote code execution." Calif의 실제 절제 발언은 "The exploit is not a universal point-and-shoot" / "Every target needs a bespoke profile"뿐이다. 절제 평가를 Calif 이름으로 내보내면 원문과 반대가 된다.

독자가 왜 몰랐나: 자바의 메모리 안전은 바이트코드와 JVM 계약의 성질이지, 그 계약을 구현하는
**손으로 쓴 스텁의 성질이 아니다.** 그런데 인트린식 목록은 길다(CRC32, AES, SHA, 배열 비교, 문자열 비교 등).
`native` 키워드가 하나도 없는 순수 자바 메서드가 사실은 어셈블리로 돌고 있었다는 사실 자체가 낯설다.

비유 후보: grep으로 찾을 수 있는 코드와, 그 자리에서 실제로 실행되는 코드가 다르다.
(비유를 글 전체로 끌고 가지 않는다 — 09-13 규율)

## 평론 각도
"패치하라"는 이미 모든 매체가 썼다. 이 글이 더할 것은 **왜 자산 목록의 키가 하나 늘어났는가**다.
소프트웨어 취약점을 "버전"으로 관리해 온 관행이, 런타임이 CPU 기능을 보고 코드를 바꿔 끼우는
순간 한 축 모자라게 된다. 그리고 그 축은 우리가 통제하지 않는다 — 클라우드가 인스턴스를 바꾸고,
하이퍼바이저가 모델을 바꿔 노출한다.
