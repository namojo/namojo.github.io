# 팩트 카드 — 2026-11-05 (KST)

## 토픽
**에이전트가 밀어 넣는 쓰기 부하에 깃허브와 오픈AI가 한 달 새 각자 깃 백엔드를 다시 설계했다.**
두 회사가 독립적으로 같은 결론에 닿았다: 합의(쿼럼/잠금)의 단위를 **저장소 전체 → 개별 레퍼런스(브랜치)**로 내린다.

## 바꾸는 것
에이전트를 팀에 들일 때 먼저 터지는 병목이 모델 비용·GPU·CI 머신이 아니라 **버전 관리의 쓰기 경로**라는 것.
독자가 내일 회의에서 쓸 문장: "에이전트가 늘면 커밋만 느는 게 아니라 **브랜치가 는다**. 저장소 단위로 잠그는 설계에서는 서로 겹치지 않는 푸시끼리도 줄을 선다."
확인할 항목: 머지 큐(메인 브랜치 한 지점 경합), 푸시당 CI 트리거 비용, 셀프호스팅 깃 서버의 복제·잠금 범위.

## 설명할 메커니즘
`git push`는 두 가지 일을 한다 — (1) **객체 전송**(파일 내용 묶음, 양은 많지만 서로 안 겹쳐 병렬 가능), (2) **레퍼런스 업데이트**(브랜치가 가리키는 커밋 해시 한 줄 교체, 합의 필요).
느린 쪽은 (2). 이유는 데이터량이 아니라 **잠금의 범위**. 저장소 전체 잠금을 레퍼런스 업데이트 내내(네트워크 왕복 포함) 쥐고 있으면, 복제본 쿼럼이 "한 번에 하나씩만 처리하는 정렬되지 않은 요청 큐"가 된다.
깃의 일관성 규칙은 원래 **레퍼런스 단위**다 → 쿼럼 범위를 레퍼런스로 내리면 서로 다른 브랜치 쓰기가 동시에 날아갈 수 있다.
비유: 층마다 다른 책을 만지는데 도서관 전체 열쇠가 하나뿐인 상황.

### GitHub 엔지니어링 블로그 ②
"The bridge to agent-scale Git infrastructure" — 2026-10-21, 저자 Eleanor White, Victoria Dye.
- 현재: "it waits for every healthy replica to respond (up to a timeout) before moving on" → 가장 느린 복제본이 지연·처리량 상한을 정함
- **"each write holds a repository-wide lock until it commits"**
- **"Holding a repository-wide lock for the entire reference update, round trips included, turns the quorum into a single, unordered request queue with one write in flight at a time."**
- 해법: **"we're changing the scope of the quorum from the whole repository to individual references."** 깃의 일관성 규칙이 레퍼런스 단위라 가능.
- 가상 쓰기 복제본이 "coalesce transactions on disjoint references into a single set of network I/Os to object storage"
- **내부 시험(realistic traffic)**: "writes to different references consistently saw 3–4x higher throughput at lower latency." ※ 프로덕션 아님, 방법론·하드웨어 미공개
- Azure 대상 지역 복제본은 데이터센터에서 약 1,000마일 → **왕복 1회 약 25ms**, "a write requires multiple round trips"
- 남는 한계: "the quorum remains the bounding factor for increasing further", "still a (small) consensus group somewhere in the stack"
URL: https://github.blog/engineering/architecture-optimization/the-bridge-to-agent-scale-git-infrastructure/

### OpenAI Pando (2026-11-02, "Scaling Git at OpenAI")
- 자사 모노레포 전용 **Rust** 깃 백엔드. 엔지니어·Codex 에이전트는 평소대로 `git push`/`git fetch`를 쓴다(호환 유지).
- **엄격한 전역 순서 대신 인과적 일관성(causal consistency)** — 여러 브랜치를 함께 읽으면 서로 다른 시점으로 보일 수 있음
- 푸시마다 **변경 불가능한 팩파일을 블롭 스토리지**에 적재, 브랜치 갱신은 **메타데이터 저장소에 새 ref 버전** 기록 → **같은 레퍼런스를 겨냥할 때만 충돌**
- 새 브랜치 푸시 시 trunk만 광고해 팩 재사용 가능하게 → 중앙값 팩 크기 **20 KiB 미만**
- 페치는 빈 팩파일 + packfile-uri 링크 목록 반환, 클라이언트는 **지역 캐시(히트율 99% 초과)**에서 내려받음
- 백그라운드 컴팩션이 작은 팩을 레벨로 병합(모노레포는 L4까지), 레벨이 스킵 리스트 역할
- 결과(**자사 측정**): **중앙값 푸시 지연 약 80% 감소**, **하루 1페타바이트에 가까운 깃 데이터** 처리
- packfile-uri 수정은 업스트림 반영, 병렬 팩 다운로드·인덱싱 등은 OpenAI 깃 포크에 존재
- **내부 전용** — 제품 아님

## 출처 바깥의 사고 (가정 — 예측 아님)
에이전트가 늘면 커밋만이 아니라 **브랜치 수**가 함께 는다(PR 하나에 브랜치 하나). 사람 하나가 하루에 브랜치 하나를 만들던 자리에 에이전트 다섯이 다섯 개를 만들면, 저장소 단위 잠금 아래에서 그 다섯은 **서로 건드리는 파일이 하나도 안 겹쳐도** 줄을 선다. 즉 에이전트가 만드는 부하의 모양은 '같은 일을 더 많이'가 아니라 **'겹치지 않는 일을 동시에'**에 가깝다.
근거: 깃허브 자신의 문장 — 수천 에이전트가 "a sustained write rate that converges on a single point in our architecture"를 만든다. 또 Octoverse의 9월 에이전트 시작 PR 1억 1천만 건은 그만큼의 브랜치를 뜻한다.
