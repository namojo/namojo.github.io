## 설명할 메커니즘 (필수)
**1) 저장소에 들어온 YAML 파일 한 장이 왜 '내 자격증명을 읽는 프로그램'인가**
- GitHub Actions의 워크플로 정의는 저장소 안의 파일이다. 기본 브랜치에 파일이 올라가는 순간
  그 자체가 실행 권한이 된다. 트리거가 `on: push`(브랜치/경로 필터 없음) + `workflow_dispatch`.
- 시크릿은 러너 안으로 환경변수/표현식으로 주입된다. 깃허브는 **로그에 찍히는 값만 마스킹**한다.
  러너에서 바깥으로 나가는 네트워크 전송은 막지 않는다. → `curl`로 POST하면 그대로 나간다.
- 그래서 공격자는 먼저 기존 워크플로 파일을 읽어 **시크릿 이름을 알아낸 뒤** 그 이름을 페이로드에 박는다.
  (Socket: kitao/pyxel의 경우 CARGO_REGISTRY_TOKEN, PERSONAL_ACCESS_TOKEN, PYPI_PASSWORD, PYPI_USERNAME)

**2) 지운 키가 왜 아직 저장소에 있는가 — 깃의 저장 구조**
- `actions/checkout`의 기본값은 `fetch-depth: 1`(최신 커밋 하나만). 이번 변종은 **`fetch-depth: 0`** 으로
  모든 브랜치·태그·커밋을 받아온다.
- 그 위에서 `git log -p --all`을 돌려 **전체 히스토리의 diff**를 훑는다. 깃에서 파일을 지우는 것은
  '새 커밋을 추가하는 일'이지 과거를 지우는 일이 아니다. 키를 담았던 블롭은 그 키를 넣었던 커밋에서
  여전히 도달 가능하다. → 2019년에 커밋했다 다음 날 지운 키도 잡힌다(StepSecurity).
- 13종 정규식: AWS(AKIA/ASIA 액세스 키 ID·시크릿 키·세션 토큰), AI 키(sk-ant-, sk-proj-, sk-or-),
  깃허브 PAT(classic·fine-grained), GitLab 토큰, Google/Firebase API 키, Slack 봇 토큰, SendGrid 키.
  히스토리 매치는 고유 300건까지 보관.
- AWS는 액세스 키 ID 전후 2줄씩을 같이 떠서(AKIA_CTX_START/END) 짝이 되는 시크릿 키를 함께 건진다.

**3) 왜 도메인 차단으로는 안 걸리는가**
- 하드코딩된 IP `193.32.204.199` 80번 포트로 평문 HTTP POST 1회(curl --data-binary, timeout 20).
- **DNS 질의가 발생하지 않는다** → 도메인 기반 통제를 우회(StepSecurity). 러너 이그레스 허용목록이 필요한 이유.

## 평론 각도
- 본문 절반 이상을 메커니즘에 쓴다: (a) 저장소 안 YAML = 실행 권한 + 로그 마스킹의 사정거리,
  (b) 깃에서 '지웠다'가 무슨 뜻인지 — 커밋 추가지 삭제가 아님, `fetch-depth: 0` + `git log -p --all`.
- 출처 바깥의 사고 1문단: 에이전트 시대에 CI 러너가 들고 있는 키의 종류가 바뀌었다는 가정
  (sk-ant-/sk-proj-/sk-or-가 13종 정규식에 올라온 것이 근거). 예측 아님을 명시.
- 사정거리 긋기: 3만 곳이 곧 3만 건 유출이 아니다. GitGuardian 1차 파동 실측은 완료 336회·유출 26건이고,
  10/9부터 깃허브가 실행 자체를 막았다. 다만 '유출되지 않았다'와 '안전하다'는 다른 얘기(StepSecurity).
- 억지 한국 접점 금지 — 포크 279개 사례로 "포크 받아 Actions 켜면 내 계정에서 돈다" 정도만.
- 마무리: 유형 8(담백한 걱정·기대형).
