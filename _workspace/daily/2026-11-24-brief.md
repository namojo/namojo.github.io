## 1차 출처 직접 인용 (검증 완료)
- 릴리스 공지(도입부): "This release introduces the `REPACK (CONCURRENTLY)` command so users can optimize tables for their current workload without disruption to ongoing operations."
- 릴리스 공지(워크로드 관리 절): "Tables that receive many updates and deletes can build up unused space, known as \"bloat,\" which can also significantly impact query performance. The `VACUUM FULL` and `CLUSTER` commands were previously used to handle this, but had tradeoffs, including preventing access to the table until the cleanup finished. PostgreSQL 19 introduces the `REPACK` command, which reclaims this space and can reorder a table's data to match an index, and with `REPACK (CONCURRENTLY)`, can do so without blocking reads or writes. `REPACK` replaces the `VACUUM FULL` and `CLUSTER` commands, both of which remain available for compatibility."
  - ⚠ 공지의 표현은 "replaces … both of which remain available for compatibility"다. "VACUUM FULL이 제거됐다"로 쓰면 오류.
- VACUUM 문서 FULL 옵션: "This option, which is deprecated, makes `VACUUM` behave like `REPACK` without a `USING INDEX` clause. This method of compacting the table takes much longer than `VACUUM` and exclusively locks the table."
- VACUUM 문서 Description: "Plain `VACUUM` (without `FULL`) simply reclaims space and makes it available for re-use. … However, extra space is not returned to the operating system (in most cases); it's just kept available for re-use within the same table."
  - 예외: TRUNCATE 옵션이 테이블 끝의 빈 페이지는 OS로 반환한다("in most cases"의 근거).
- REPACK 문서 잠금: "When the `CONCURRENTLY` option is specified, the bulk of the operation is run with `SHARE UPDATE EXCLUSIVE` lock, and the `ACCESS EXCLUSIVE` lock is only acquired during the final phase to swap the table and index files."
- REPACK 문서 변경 포착 방식: "The data changes that took place during the creation of the new table and index files are captured using logical decoding … and applied before the `ACCESS EXCLUSIVE` lock is requested. Once that lock is obtained, a final pass over any remaining captured concurrent data changes is done and the files are swapped. Thus the lock is typically held for a short time, depending on the amount of changes accumulated while the lock was being waited for."
- REPACK 문서 디스크: "REPACK creates a temporary copy of the table and all of its indexes, so you need free disk space at least equal to the sum of the table size and the index sizes."
- REPACK 문서 동시 변경 상한: "if more than about 104 million rows are concurrently updated or deleted during the execution of `REPACK`, the command fails."
- REPACK 문서 CONCURRENTLY 사용 불가 조건 (원문 목록):
  - 테이블이 아님(예: 구체화 뷰) / UNLOGGED 테이블 / 파티션 테이블 / 기본 키와 인덱스 기반 replica identity가 없음 / 시스템 카탈로그·TOAST 테이블 / 접근 방식이 `heap`이 아님 / `user_catalog_table` 스토리지 파라미터로 선언됨 / 트랜잭션 블록 안에서 실행 / `max_repack_replication_slots`가 추가 복제 슬롯 생성을 허용하지 않음
- REPACK 문서 MVCC: "REPACK with the CONCURRENTLY option is not MVCC-safe. After the repacking transaction commits, the table will appear empty to concurrent transactions, if they are using a snapshot taken before repacking started."
- REPACK 문서 DDL: "REPACK (CONCURRENTLY) might fail to complete if DDL commands are executed on the table by other transactions during the repacking."
- 예시 구문: `REPACK (CONCURRENTLY) employees USING INDEX;`

## 바꾸는 것
PostgreSQL을 운영하는 팀이 "불어난 테이블을 정리하려면 서비스를 세워야 한다"는 전제를 버릴 수 있게 된다. 동시에 **그냥 쓸 수 있는 기능이 아니다** — 내일 회의에서 써먹을 확인 목록이 바로 나온다.
- 우리 테이블에 **기본 키(또는 인덱스 기반 replica identity)가 있는가** — 없으면 CONCURRENTLY 자체가 거부된다.
- **테이블+인덱스 전체 크기만큼의 여유 디스크**가 있는가 (디스크가 차서 정리하려는 상황이면 이 조건부터 안 맞는다).
- **파티션 테이블·UNLOGGED 테이블은 대상이 아니다** (개별 파티션은 가능 — 문서 본문이 아니라 PostgreSQL 19 서버의 HINT "Consider running the command on individual partitions"가 근거. 본문에서 문서에 귀속시키지 말 것).
- **복제 슬롯을 하나 더 쓴다**(`max_repack_replication_slots`) — 슬롯 예산을 쓰고 있는 환경이면 설정부터 확인.
- 마지막 파일 교체 때 ACCESS EXCLUSIVE를 잠깐 잡는다 → **장기 실행 쿼리가 테이블을 붙들고 있으면 그 '잠깐'이 길어지고, 그 뒤로 모두가 줄을 선다.**
- pg_repack 확장을 쓰던 팀은 외부 확장 의존을 코어 기능으로 옮길 수 있는지 검토 대상.

## 설명할 메커니즘
**"행을 지웠는데 디스크가 줄지 않는다"의 전 과정.** 독자(특히 애플리케이션 개발자)가 가장 흔히 모르는 것.
1. **MVCC**: PostgreSQL의 UPDATE는 제자리에서 값을 고치지 않는다. 새 행 버전을 쓰고 옛 버전을 죽은 것으로 표시한다. DELETE도 표시만 한다. 이유 — 그 시점의 스냅샷을 들고 있는 다른 트랜잭션에게는 옛 버전이 아직 보여야 하기 때문. 그래서 테이블 파일은 '산 행과 죽은 행이 섞인 더미'가 된다.
2. **VACUUM이 하는 일과 안 하는 일**: 죽은 행이 차지한 자리를 **같은 파일 안에서 재사용 가능하게** 표시할 뿐, 대개 OS에 돌려주지 않는다(끝쪽 빈 페이지만 TRUNCATE로 반환). 그래서 파일 크기는 그대로다 = bloat. 순차 스캔이 그 빈 공간까지 읽으므로 조회 성능도 깎인다.
3. **옛 처방이 아팠던 이유**: VACUUM FULL은 테이블을 새 파일로 통째로 다시 쓴다. 그동안 ACCESS EXCLUSIVE 잠금 → 읽기도 쓰기도 전부 차단. 큰 테이블이면 몇 시간.
4. **REPACK CONCURRENTLY가 다른 지점(핵심)**: 복사하는 동안 들어오는 변경을 **logical decoding으로 포착**한다. 즉 WAL 스트림을 읽어 따라잡는다 — 논리 복제와 같은 기계장치이고, 그래서 복제 슬롯을 하나 쓴다. 복사본을 만들고 → 밀린 변경을 적용하고 → 그제서야 ACCESS EXCLUSIVE를 잡아 파일을 바꿔 끼운다. 잠금 시간이 '테이블 크기'에서 '대기하는 동안 쌓인 변경량'으로 바뀐 것이 요점.
   - 독자가 아는 기본형과의 대조: 그동안 같은 일을 하던 `pg_repack` 확장은 트리거로 변경을 로그 테이블에 받아 적는 방식이었다. 코어의 REPACK은 그 자리에 복제 메커니즘을 가져다 놓았다. (pg_repack 공식 문서 1차 확인 완료: 1)로그 테이블 생성 2)원본에 트리거 부착 4)로그 재생 5)카탈로그로 스왑)
5. 부작용: MVCC-safe하지 않다. 리팩 시작 전 스냅샷을 든 트랜잭션에게는 테이블이 **비어 보인다.**

- 출처 바깥의 사고(가정임을 명시 + 근거): **불어난 테이블을 정리해야 한다는 걸 깨닫는 순간은 대개 디스크가 찼을 때인데, 그때가 바로 "테이블+인덱스 크기만큼의 여유 디스크"를 댈 수 없는 순간이다.** 근거는 문서가 스스로 적어 둔 디스크 요구량과 잠금 대기 조건. 예측이 아니라 조건을 겹쳐 본 가정.
