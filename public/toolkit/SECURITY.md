# 보안 설계 노트

이 문서는 "서버가 없으니 안전하다"는 착각을 걷어내는 데 목적이 있습니다.
서버가 없으면 서버측 공격면(SQLi, 인증우회, 업로드 취약점, 계정 유출)이 사라지는 것은 사실이지만,
클라이언트 사이드 도구 사이트의 위험은 전부 **브라우저 안, 오리진 안쪽**에 남습니다.

## 위협 모델

| # | 위협 | 왜 이 유형에서 현실적인가 | 이 프로젝트의 대응 |
|---|---|---|---|
| T1 | DOM-based / 저장형 XSS | 도구의 본질이 "사용자 입력 → 화면 렌더". 결과를 `innerHTML` 로 그리면 즉시 성립 | `textContent` / DOM API 전용, `innerHTML` 전면 금지, CSP `script-src 'self'` |
| T2 | 오리진 공유로 인한 피해 확산 | `namojo.github.io` 는 **단일 오리진**. 블로그·기존 프로젝트·도구 전부가 같은 저장소를 공유 | 도구를 `sandbox="allow-scripts"` iframe(불투명 오리진)에서 실행 |
| T3 | 서드파티 스크립트의 DOM 접근 | 같은 페이지의 광고·애널리틱스는 그 페이지 DOM 전체에 접근 가능. "전달하지 않는다"는 정책은 코드로 보장되지 않음 | `sensitive: true` 페이지에는 빌드가 트래커를 **주입하지 못하게** 차단 |
| T4 | CDN 공급망 침해 | `@latest` 로 불러오는 라이브러리는 CDN 침해 시 즉시 임의 코드 실행 | 외부 CDN 미사용. 라이브러리가 필요하면 `vendor/<lib>@<정확한 버전>/` 로 저장소에 고정 |
| T5 | 파서 자체의 취약점 | 신뢰할 수 없는 파일을 내 오리진 안 파서에 먹이는 구조. PDF.js 는 **CVE-2024-4367**(4.2.67 미만, 악성 PDF 하나로 임의 JS 실행) 이력이 있음 | 현재 외부 파서 미사용. 도입 시 버전 고정 + Dependabot 감시 + 샌드박스 안에서만 실행 |
| T6 | 민감 데이터의 저장소 잔류 | 공용 PC 에서 다음 사용자가 앞사람의 문서를 열어 봄 | `TK.storage` 에는 옵션만. 입력 내용은 메모리에만 |
| T7 | 브리지 권한 상승 | 도구가 다른 도구의 저장소를 읽거나 오리진 저장소를 채워 다른 페이지를 망가뜨림 | 네임스페이스는 허브가 결정, 키 형식 검증, 32KB 상한 |
| T8 | 탭내빙 / 클릭재킹 | 외부 링크와 iframe 임베드 | 모든 외부 링크 `rel="noopener noreferrer"`. 클릭재킹은 아래 "막을 수 없는 것" 참조 |

## 격리가 실제로 어떻게 동작하는가

허브가 도구를 이렇게 띄웁니다.

```html
<iframe sandbox="allow-scripts allow-downloads"
        allow="clipboard-write"
        referrerpolicy="no-referrer"></iframe>
```

`allow-same-origin` 을 **주지 않은** 것이 핵심입니다. 그러면 그 문서는 불투명 오리진을 받고,
같은 도메인에 놓여 있어도 `namojo.github.io` 의 `localStorage`·쿠키·다른 창에 접근할 수 없습니다.
방마다 자물쇠를 다는 대신 방 자체를 다른 건물로 옮기는 접근입니다.

부작용으로 도구 자신도 `localStorage` 를 못 쓰게 되는데, 그 구멍을 브리지가 메웁니다.

```
[허브]  ──── hello ────▶  [도구]        허브가 먼저 인사한다.
                                        도구는 event.origin(브라우저가 보증)을 기록하고
                                        이후 응답을 그 오리진으로만 보낸다.

[도구]  ── set(key,v) ─▶  [허브]        허브의 검증:
                                          1. e.source === 지금 열린 iframe.contentWindow 인가
                                          2. key 가 /^[a-z0-9][a-z0-9_-]{0,39}$/ 인가
                                          3. 직렬화 크기가 32KB 이하인가
                                          4. 네임스페이스는 "허브가 아는 도구 id" 로 붙인다
                                             → tk:tool:<activeToolId>:<key>
```

4번이 결정적입니다. **도구는 자기 이름표를 정할 수 없습니다.**
`key: "../table-tidy:opts"` 로 남의 서랍을 열려는 시도는 2번에서 걸려 `ok: false` 로 거부되고,
실제 저장은 일어나지 않습니다 (`verify/browser-check.mjs` 의 "네임스페이스 탈출 차단" 항목이 이걸 검증합니다).

## 기본선 체크리스트

새 도구를 추가할 때마다 확인합니다.

- [ ] `innerHTML` / `insertAdjacentHTML` / `document.write` / `eval` / `new Function` / 문자열 `setTimeout` 없음
- [ ] 사용자 입력이 화면에 닿는 모든 경로가 `textContent` 또는 `createElement` 기반
- [ ] `tools.json` 에 `network` 를 정직하게 선언 (기본은 `none`)
- [ ] `sensitive: true` — 사용자의 문서·이미지·표를 다루면 예외 없이
- [ ] `TK.storage` 에 옵션만 저장. 입력 내용·파일명·결과물 저장 금지
- [ ] 입력 크기 상한과 초과 시 안내 문구
- [ ] 외부 링크에 `rel="noopener noreferrer"`
- [ ] 인라인 `<style>` / `style=""` / 인라인 `<script>` 없음 (CSP 에 걸림)
- [ ] 라이브러리를 쓴다면 `vendor/` 에 정확한 버전으로 고정 (CDN + `@latest` 금지)
- [ ] `node scripts/build.mjs` 통과 + `node verify/browser-check.mjs` 통과

## 막을 수 없는 것 — 정직한 목록

**1. 응답 헤더**
GitHub Pages 는 커스텀 응답 헤더를 지원하지 않습니다. CSP 를 `<meta http-equiv>` 로만 적용하므로
`frame-ancestors`, `report-uri`, `sandbox` 지시어는 무시됩니다. 즉 **클릭재킹을 헤더로 막을 수 없습니다.**
도구가 로그인이나 결제를 다루지 않으므로 현재 영향은 낮지만, 그런 기능을 붙일 계획이라면
헤더를 제어할 수 있는 호스팅(Cloudflare Pages, Netlify 등)으로 옮기는 것이 먼저입니다.

**2. 브라우저 간 CSP 동작 차이**
샌드박스 문서는 불투명 오리진을 갖는데, 그 안에서 `script-src 'self'` 가 자기 스크립트를 허용하는지는
구현에 따라 다를 수 있습니다. **Chromium 에서는 실측으로 동작을 확인했습니다.**
Firefox·Safari 에서 도구가 빈 화면으로 나오면 이 지점이 원인입니다. 그때의 처방:

```js
// scripts/build.mjs 의 buildCSP() 에서
'script-src': `'self' ${site.baseUrl}`,   // 명시적 호스트를 함께 나열
```

로컬 http 테스트를 위해서는 `http://127.0.0.1:8099` 도 함께 넣은 개발용 빌드가 필요합니다.

**3. 같은 오리진 자체**
격리는 허브를 통해 열었을 때 적용됩니다. 사용자가 도구 URL을 직접 열면(SEO·공유 링크로는 그게 정상입니다)
그 페이지는 `namojo.github.io` 오리진에서 돕니다. 그래서 T1(XSS 금지)은 격리와 **별개로** 지켜야 하는
1차 방어선입니다. 격리는 2차 방어선입니다.

**4. 조직 규정**
데이터가 기기를 벗어나지 않는다는 기술적 사실과, 사내 문서를 외부 웹 도구에 입력해도 되는지는
별개 문제입니다. 후자는 코드로 해결되지 않습니다.

## 광고를 붙이기로 결정한다면

수익화를 하더라도 도구 페이지는 예외로 두는 것을 권합니다. 개인정보 익명화 도구 페이지에
광고 스크립트를 올리는 것은 설계상 자기모순입니다.

- `site.json` 의 `tracker.snippet` 에 넣으면 `sensitive: false` 페이지(허브·소개)에만 들어갑니다
- 도구 페이지의 CSP 는 `script-src 'self'` 이므로, 광고를 넣으려면 CSP 를 열어야 합니다.
  **CSP 를 여는 순간 T3 방어가 사라진다**는 점을 기억하세요
- EN 버전을 운영하며 AdSense 를 쓰면 EU 사용자에 대해 동의 관리 플랫폼(CMP)이 정책상 요구됩니다.
  광고를 넣지 않으면 이 문제 자체가 없습니다 (법률 조언이 아니며, 필요하면 전문가 확인 권장)
