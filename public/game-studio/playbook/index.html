Idea 1 · Compliance Gate

확률형 아이템 공시 게이트

목표는 하나입니다. 확률 숫자가 틀리거나, 바뀌었는데 공시 갱신일이 그대로인 데이터는 커밋조차 되지 않게 만듭니다. 사람이 체크리스트로 지키던 규칙을 코드로 옮기는 작업입니다.

담당라이브 기획 + 클라이언트 1시간반나절전제0단계 + 키트 설치

1-1지금 확률 데이터가 어디에, 어떤 형식으로 있는지 파악

Assets 폴더와 서버 설정 폴더에서 소환(가챠) 확률 테이블이 어디에 어떤 형식(JSON, CSV, ScriptableObject, DB 덤프)으로 있는지 찾아서 표로 정리해 줘. 파일은 수정하지 마.

결과에 따라 갈래가 나뉩니다.

  • 이미 JSON → 1-2로 바로 가서 키트 형식에 맞춥니다.
  • CSV·ScriptableObject·DB → 공시의 기준이 될 JSON을 뽑아 내는 변환 스크립트를 먼저 만듭니다(아래 프롬프트).
tools/export_gacha.py 를 만들어 줘. 위에서 찾은 소환 확률 원본을 읽어서 assets/data/gacha/gacha_{배너ID}.json 형식(키트의 gacha_sample_pickup.json 과 같은 키)으로 내보내는 스크립트야. 원본은 절대 수정하지 말고, 쓰기 전에 경로를 먼저 물어봐.

공시의 "진짜 원본"을 무엇으로 볼지 정합니다. 서버 DB가 진짜라면, JSON은 그 DB에서 뽑은 사본이고 배포 파이프라인에서도 같은 검사를 돌려야 합니다(1-6).

1-2데이터를 키트 형식으로 맞추기

파일 하나에 배너 하나. 이름은 gacha_[배너].json, 키는 snake_case(CCGS 데이터 규칙)입니다. 확률은 퍼센트 값입니다.

키내용검사 규칙
grades[].rate등급 확률(%)모든 등급 합 = 100
grades[].items[].rate아이템 확률(%)등급 안 합 = 그 등급 확률, 소수 4자리 이내, 아이템 중복 금지
pity천장 {enabled, guaranteed_grade, pulls}보장 등급이 실제로 있어야 함
disclosure.updated_at공시 갱신일 YYYY-MM-DD확률·천장이 바뀌면 반드시 바뀌어야 함
disclosure.text_ko공시 안내 문구비어 있으면 실패
 
python tools\check_gacha.py --all
✓ assets/data/gacha/gacha_sample_pickup.json
✗ assets/data/gacha/gacha_halloween.json
  - 등급 SR: 아이템 확률 합 17.5% ≠ 등급 확률 18%

모든 파일에 ✓가 붙을 때까지 고칩니다. --all은 git이 추적하는 파일만 보므로 새 파일은 먼저 git add 하세요.

Claude에게 확률을 하나 바꾸고 커밋하라고 시켜 봅니다. 공시 갱신일은 그대로 둡니다.

gacha_sample_pickup.json 에서 hero_ara 확률을 0.8로, SSR 등급 확률을 2.1로, R 등급의 hero_han 을 39.9, R 등급을 79.9로 바꾸고 "test: 확률 조정"으로 커밋해 줘. updated_at 은 건드리지 마.
✗ assets/data/gacha/gacha_sample_pickup.json
  - 확률 구성이 바뀌었는데 disclosure.updated_at(2026-10-23)이 그대로입니다 — 공시 갱신일을 고치고 공지를 준비하세요

1-4사람이 하는 커밋에도 같은 검사 걸기

중요: Claude Code 훅은 Claude가 실행하는 명령만 지킵니다. 사람이 IDE나 SourceTree로 커밋하면 지나갑니다. git 자체의 pre-commit 훅에도 같은 검사기를 연결하세요.

# -NoNewline: 줄 끝에 CRLF가 붙으면 sh가 "exit 1\r"을 읽지 못한다
Set-Content -NoNewline -Encoding ascii .git\hooks\pre-commit "#!/bin/sh`npython tools/check_gacha.py --staged || exit 1`n"

SourceTree에서 틀린 데이터를 커밋하면 같은 오류로 실패합니다. 이 훅은 PC마다 설치해야 하므로 신규 입사자 셋업 문서에 넣으세요. 팀 전체에 강제하려면 1-6의 CI 검사가 최종 방어선입니다.

1-6배너마다 검수 에이전트 돌리기 + CI에 걸기

gacha-compliance 에이전트로 assets/data/gacha/gacha_sample_pickup.json 과 notice-table.md 를 design/live-ops/ethics-policy.md 기준으로 검수하고 결과를 production/qa/gacha-review-sample.md 에 써 줘.

마지막 줄에 PASS 또는 BLOCKED가 나옵니다. BLOCKED 항목에는 파일·키·고칠 방법이 적혀 있습니다.

빌드 서버(GitHub Actions, Jenkins 등)에 한 줄을 추가하면 어떤 경로로 들어온 데이터도 막을 수 있습니다.

윤리 정책(design/live-ops/ethics-policy.md)의 빈칸 — 천장 상한, 미성년자 결제 정책 링크 — 을 기획·법무가 채웁니다. 이 문서가 비어 있으면 검수 에이전트도 기준 없이 판단하게 됩니다.

live-ops-designer의 다른 원칙(스태미나 금지, P2W 금지)은?

install_kit.py는 랜덤 박스 관련 두 문장만 바꿉니다. "인위적인 스태미나 시스템 금지", "P2W 금지" 같은 원칙은 그대로 남겨 두었으니, 우리 게임 구조에 맞게 유지할지 고칠지 팀이 정하고 .claude/agents/live-ops-designer.md의 "Ethical Guidelines" 절을 직접 수정하세요.

Idea 3 · 2-Week Kill or Go

캐주얼 신작 2주 검증

설계 문서 30개보다 플레이해 볼 수 있는 시제품 하나가 낫다는 것이 원작자 실험의 결론이었습니다. 한 장짜리 기획서 → 버리는 시제품 → 플레이테스트 → 진행·전환·중단 판정을 10영업일에 끝냅니다.

담당기획 1 + 프로그래머 1시간10영업일전제0단계 중 A(새 레포), rigor minimal
D1가설·중단 기준
D2한 장 기획서
D3–6시제품
D7–9플레이테스트
D10판정 회의

3-1D1 — 검증할 질문과 중단 기준을 먼저 적기

판정 날에 기준을 정하면 늘 "조금만 더"가 됩니다. 첫날 문서로 박아 둡니다.

design/kill-criteria.md 를 만들어 줘. 검증할 질문은 "머지 퍼즐에 방치형 성장을 붙이면 첫 3분 안에 '한 판 더'가 나오는가".
PROCEED 기준: 테스터 8명 중 5명 이상이 요청 없이 2판째를 시작.
KILL 기준: 3명 이하. 그 사이면 PIVOT. 쓰기 전에 경로를 확인해 줘.

질문은 하나만. "재미있는가"처럼 넓은 질문은 판정이 안 됩니다.

3-2D2 — 한 장짜리 기획서

/brainstorm 머지 퍼즐 + 방치형 성장, 세로 화면 한 손 조작

minimal에서는 대화 몇 번으로 끝나는 "린 브리프" 흐름이 돕니다. 한 줄 컨셉 2~3개 중 하나를 고르면 제목·피치·코어 루프·승패 조건·MVP(최대 7개)·제외 범위·만드는 순서를 채워 design/game-brief.md에 씁니다.

MVP가 7개를 넘으면 에이전트가 먼저 "너무 길다"며 덜어 낼 항목을 제안합니다. 그게 정상입니다.

3-3D3–6 — 버리는 시제품 만들기

/prototype 머지 3단계와 오프라인 보상만 있는 한 화면 --path html

--path는 세 가지입니다. 처음엔 html을 권합니다 — 휴대폰 브라우저로 바로 돌려 볼 수 있어 빌드 시간이 0입니다. 손맛(터치 반응, 연출)이 질문의 핵심이면 engine, 규칙만 보면 되면 paper를 고릅니다.

코드는 prototypes/ 아래에만 생깁니다. 이 폴더엔 느슨한 규칙(prototype-code.md)이 적용되고, 가설이 적힌 README가 필수입니다.

시제품 코드를 본 개발에 그대로 쓰고 싶어진다

쓰지 마세요. 시제품은 속도를 위해 기준을 낮춘 코드입니다. PROCEED가 나면 3-5처럼 스토리로 다시 만듭니다. 쓰기 훅(validate-write.sh)도 시제품 경계를 넘는 쓰기에 경고를 냅니다.

3-4D7–9 — 플레이테스트 기록과 분석

/playtest-report new

관찰 양식(첫 5분 인상, 흐름, 버그, 정량 데이터)이 나옵니다. 다른 팀 동료 8명에게 설명 없이 휴대폰을 건네고, 한 명당 양식 하나씩 메모합니다. "2판째를 스스로 시작했는가"를 반드시 적으세요.

/playtest-report analyze production/playtests/2026-11-merge-notes.md

세션별 피드백이 정리되고 다음에 손댈 우선순위 상위 3개가 나옵니다. "design/kill-criteria.md 기준과 비교해 줘"를 덧붙이면 판정 기준 대비 결과도 함께 봅니다.

3-5D10 — 판정하고 다음 걸음

/prototype은 마지막에 PROCEED / PIVOT / KILL / NOT ASSESSED 중 하나로 보고서를 쓰고 creative-director 검토를 붙입니다. 아무도 처음부터 끝까지 플레이해 보지 않았으면 NOT ASSESSED입니다 — 추측으로 PROCEED를 주지 않습니다.

최종 결정은 회의에서 사람이 합니다. 보고서는 근거 자료입니다.

# PROCEED라면 — 본 개발 모드로
/settings modes.rigor=standard
/create-stories

KILL이어도 실패가 아닙니다. 2주 만에 "만들지 말 것"을 하나 알아낸 것입니다. 보고서는 다음 아이디어의 근거로 남겨 둡니다.

Idea 4 · Legacy to Docs

운영 중인 RPG 역문서화 & 온보딩

핵심 원칙은 교체가 아니라 이전(migration)입니다. CCGS는 있는 것을 다시 만들지 않고 빠진 것만 채웁니다. 코드에서 읽어 낼 수 있는 "무엇"은 에이전트가, 코드에 없는 "왜"는 담당자가 답합니다.

담당리드 프로그래머 + 시니어 기획시간1~2주(시스템 3개 기준)전제0단계 중 B(이식), 별도 브랜치

/project-stage-detect

영역별 완성도 개요, 빠진 문서 목록(Gaps), 추천 다음 단계가 나옵니다. 설계 문서가 하나도 없는 운영 프로젝트라면 거의 모든 칸이 비어 있는 게 정상입니다.

4-2이전 계획 세우기

있는 문서(기획서, 위키 내보내기 등)를 CCGS 형식 기준으로 감사하고, 빈칸을 BLOCKING/HIGH/MEDIUM/LOW로 분류한 순서 있는 계획을 docs/adoption-plan-[날짜].md로 씁니다. 범위를 좁히려면 /adopt gdds, /adopt infra처럼 줍니다.

계획에서 먼저 문서화할 핵심 시스템 3개를 고릅니다. 추천: 담당자가 한 명뿐인 시스템, 장애가 잦은 시스템, 신규 입사자가 가장 먼저 만지는 시스템.

4-3코드에서 설계 문서를 거꾸로 쓰기

/reverse-document design Assets/Scripts/Gacha
/reverse-document design Assets/Scripts/Battle
/reverse-document architecture Assets/Scripts/Core

한 번에 하나씩 실행합니다. 에이전트가 코드를 분석한 뒤 "왜 이렇게 했는지"를 묻는 질문을 합니다. 예: "천장 카운트가 배너 간에 이월되는데 의도인가요?" 담당자가 답한 내용이 문서의 핵심 가치입니다.

초안을 보여 주고 승인을 받은 뒤 design/gdd/ 또는 docs/architecture/에 씁니다. 코드가 너무 적어 문서화할 게 없으면 스스로 "부족함"을 판정하고 멈춥니다.

문서에 코드 추정과 확인된 사실이 섞인다

프롬프트 끝에 "담당자가 확인한 내용은 [확인], 코드에서 추정한 내용은 [추정]으로 표시해 줘"를 붙이세요. 리뷰할 곳이 바로 보입니다.

4-4역할별 온보딩 문서 만들기

/onboard client-programmer
/onboard live-ops-designer

프로젝트 요약, 역할, 아키텍처, 지켜야 할 규칙, 담당 영역 현황, 흔한 함정, 첫 과제, 물어볼 질문 목록이 담긴 문서가 나옵니다. 다음 입사자에게 실제로 건네 보고 빠진 점을 받아 고칩니다.

Idea 5 · Mobile Budget & QA

저사양 기기 성능 예산 & 출시 QA

"느려진 것 같다"를 숫자로 바꾸는 작업입니다. CCGS는 예산이 비어 있으면 통과라고 하지 않고 NOT ASSESSED(판정 불가)라고 답합니다. 그래서 첫 단계는 예산을 적는 것입니다.

담당클라이언트 리드 + QA시간기준 수립 1주, 이후 매 업데이트 30분전제0단계 + 키트(설정 조각)

5-1최저 지원 기기 기준으로 예산 적기

키트의 snippets/project-yaml-mobile.yaml을 참고해 project.yaml의 platform·performance 블록을 고칩니다. 값은 가장 낮은 지원 기기(Tier C) 기준입니다 — 거기서 통과하면 나머지도 통과합니다.

/settings performance.target_framerate=30
/settings performance.frame_budget_ms=33.3
/settings performance.memory_ceiling_mb=1200
/settings performance.draw_call_limit=150

숫자는 예시입니다. 5-2의 실측 뒤에 확정하고, 그 전까지 performance.enforce는 warn으로 둡니다.

5-2실기기 기준선 측정

키트의 docs/performance/device-tiers.md에 등급별 대표 기기와 목표를 적고, Tier C 실기기에서 Unity Profiler(개발 빌드)로 로비·전투·소환 연출을 각 3분씩 측정합니다. 결과는 production/qa/perf/에 날짜별로 남깁니다.

이 측정은 사람이 합니다. Claude는 실기기를 만질 수 없습니다. 대신 측정 결과를 정리시킬 수 있습니다.

production/qa/perf/2026-10-28-tierC.csv 는 Galaxy A 시리즈 실기기 측정값이야. 구간별 평균·1% Low FPS, 최대 메모리를 device-tiers.md 의 예산과 비교한 표로 정리해 줘.

5-3코드 수준 병목 찾기

/perf-profile full

예산 대비 판정과 순위가 매겨진 최적화 후보(핫패스 할당, Update 남용, 과도한 Draw Call 원인 등)가 나옵니다. 실측 데이터 없이 코드만 본 항목은 그렇다고 표시됩니다.

5-4테스트 기반 깔기 (한 번만)

Unity Test Framework 기준으로 테스트 폴더 구조와 실행 명령(project.yaml의 commands.test)을 맞추고, 자주 쓰는 픽스처·헬퍼를 만듭니다.

# QA에 넘기기 전 — 실패하면 QA 준비 안 된 빌드
/smoke-check --platform mobile

adb exec-out screencap -p > production\qa\evidence\story-042-lobby.png

Idea 6 · Global Launch

글로벌 출시 현지화 파이프라인

/localize 하나에 하위 명령 10개가 있습니다. 순서대로 밟으면 코드 속 하드코딩 문자열 찾기 → 문자열 표 추출 → 번역 브리프 → 검증 → 문화 검토 → 동결 → 현지화 QA가 됩니다.

담당현지화 담당 + 클라이언트 1시간출시 4~6주 전 시작전제0단계

6-1하드코딩 문자열 찾고 표로 뽑기

/localize scan
/localize extract

scan은 코드·UI에 박힌 문자열 목록을, extract는 키가 붙은 문자열 표를 만듭니다. 바꾼 코드는 다음 빌드에서 화면이 그대로인지 꼭 확인합니다.

6-2번역 브리프 만들기

/localize brief

번역 업체나 번역가에게 그대로 넘길 문서입니다. 게임 개요, 말투, 캐릭터 용어집, 세계관 용어집, 번역 금지 목록, 플레이스홀더({0} 등) 설명, 글자 수 제한이 들어갑니다.

캐릭터 이름을 현지화할지 음차할지 같은 결정은 브리프를 보내기 전에 사람이 확정합니다.

6-3번역본 검증과 문화 검토

/localize validate
/localize cultural-review
/localize rtl-check      # 아랍어 등 오른쪽→왼쪽 언어가 있을 때만

validate는 누락 키, 깨진 플레이스홀더, 글자 수 초과를 잡습니다. cultural-review는 숫자·색·제스처·종교 표현처럼 지역별로 문제가 될 수 있는 항목을 짚습니다.

6-4문자열 동결

/localize freeze

동결 이후 문자열을 바꾸려 하면 쓰기 훅(validate-write.sh)이 "동결이 활성 상태이니 변경을 Post-Freeze Changes에 기록하거나 동결을 먼저 해제하라"는 경고를 냅니다. 막지는 않고 알립니다.

6-5현지화 QA, 출시 판정, 데이원 패치

/localize qa
/launch-checklist 2026-12-01
/day-one-patch known-bugs

/launch-checklist는 코드·콘텐츠·QA·스토어·인프라·커뮤니티·운영 7개 영역을 훑고, 사람만 확인할 수 있는 항목(스토어 심사 상태, 법무 승인 등)을 따로 묻습니다. 출시 직후 문제는 /day-one-patch가 롤백 계획과 QA 게이트를 갖춘 작은 스프린트로 처리합니다.

Go/No-Go는 체크리스트 결과를 보고 사람이 서명합니다.

막힐 때

훅이 하나도 안 도는 것 같다

Claude Code를 CLAUDE.md가 있는 루트에서 띄웠는지 확인하세요. 하위 폴더에서 띄우면 훅·차단 규칙이 로드되지 않습니다. 설정을 바꾼 뒤에는 세션을 다시 시작해야 합니다.

승인 창이 너무 자주 뜬다

설계상 정상입니다(파일을 쓰기 전에 묻는다). 익숙해지면 /settings --local modes.automation=guided로 막힌 단계에서만 멈추게 할 수 있습니다. 팀 전체 설정이 아니라 내 PC에만 적용됩니다.

대답이 영어로 나온다

0-6의 "Team Language" 한 줄을 CLAUDE.md에 넣었는지 확인하세요. 문서 파일 본문을 한국어로 받고 싶다면 그 줄에 "Write design documents in Korean"도 추가합니다.

비용이 걱정된다

디렉터 리뷰가 가장 비쌉니다. review_mode: solo(0-6)로 시작하고, 파일럿 2주 동안 사용량을 본 뒤 중요한 시스템만 system_overrides로 리뷰를 강화하세요.

스킬을 고쳤더니 이상하게 동작한다

스킬 파일을 고치면 훅이 /skill-test를 권합니다. /skill-test static [스킬명]으로 구조 검사부터, /skill-improve [스킬명]으로 점수가 떨어지면 되돌리는 개선 루프를 돌릴 수 있습니다.

회사 보안 정책상 소스를 외부 AI에 보내도 되는지 모르겠다

도입 전에 사내 AI 사용 정책부터 확인하세요. 기술적으로는 CCGS 권한 규칙이 .env 읽기를 막지만, 서버 키·결제 설정이 있는 레포라면 그 파일들을 레포 밖으로 빼거나 .claude/settings.json의 deny 목록에 경로를 추가하세요.
