Session 0 · 세미나 전에

시작 전 준비

모델 파일이 수 기가바이트입니다. 당일에 받으면 실습 시간의 절반이 다운로드로 갑니다. 전날까지 끝내 주세요.

어떤 모델을 돌릴 수 있는지는 VRAM(그래픽카드 메모리)이 정합니다. 본체 RAM이 아닙니다.

PowerShell
nvidia-smi

# NVIDIA 그래픽카드가 없다면
wmic path win32_VideoController get name,AdapterRAM

nvidia-smi 출력의 Memory-Usage 오른쪽 숫자가 전체 VRAM입니다.

Terminal
system_profiler SPHardwareDataType | grep -E "Chip|Memory"

애플 실리콘(M1~M5)은 통합 메모리라 본체 RAM을 GPU와 나눠 씁니다. RAM 16GB면 VRAM 8GB급으로 생각하면 대체로 맞습니다.

Terminal
nvidia-smi
lspci | grep -i vga
GPU가 없어도 참여할 수 있습니다 CPU만으로도 작은 모델은 돕니다. 느릴 뿐입니다. 아래 표의 맨 윗줄을 보세요. 세션 3의 하네스 조립은 모델 성능과 거의 무관하므로, 느린 모델로도 끝까지 따라올 수 있습니다.

양자화 표기 읽는 법 Q4_K_M의 4는 가중치 하나를 몇 비트로 저장하는가입니다. 필요한 메모리는 대략 파라미터 수 × 비트 ÷ 8이고, 여기에 컨텍스트 몫이 더 붙습니다. 8B 모델을 4비트로 담으면 약 4GB이니 VRAM 8GB면 여유가 있습니다.

MoE는 조금 다릅니다. 토큰마다 전문가 일부만 계산에 쓰이므로 속도는 작은 모델급이지만, 가중치 전체가 메모리에 올라가 있어야 해서 용량은 큰 모델급입니다. 속도와 용량을 따로 봐야 합니다.

모델 이름과 태그는 자주 바뀝니다. 실행 전 ollama.com/library에서 현재 쓸 수 있는 태그를 확인하세요.

ollama.com/download에서 설치 파일을 받아 설치하고, nodejs.org에서 LTS 버전을 설치합니다. 그다음 확인합니다.

확인

node -v     # v20 이상이면 됩니다
위 표에서 고른 모델로
ollama pull qwen3:8b

ollama list에 모델이 보이면 준비가 끝난 것입니다.

Session 2 · 19:55~20:40 · 45분

하네스의 바닥 깔기 — 모델과 런타임

모델을 내 PC에 올리고 에이전트에 연결합니다. 그리고 왜 이것만으로는 부족한지를 직접 확인합니다.

왜 내 PC인가

비용과 보안이 흔히 드는 이유지만, 하네스 관점에서 더 중요한 건 세 번째입니다. 몇 번이고 다시 돌릴 수 있는가. 하네스는 같은 작업을 반복 실행하면서 다듬어 가는 구조라, 실행 한 번에 돈이 나가면 사람이 실험을 아끼게 됩니다. 아끼는 순간 하네스는 자라지 않습니다.

Terminal
ollama run qwen3:8b

프롬프트가 뜨면 아무 말이나 걸어 보고, /bye로 빠져나옵니다.

에이전트 런타임은 대화창이 아니라 API로 모델을 부릅니다. 그 통로가 열려 있는지 봅니다.

Terminal
curl http://localhost:11434/api/tags

설치한 모델 목록이 JSON으로 돌아오면 됩니다. Ollama는 설치되면 11434 포트에서 계속 떠 있습니다.

세미나에서는 길드가 안내하는 런타임(OpenClaw·Hermes 등)을 함께 설치하고 위 localhost:11434를 모델 공급자로 지정합니다. 설정 화면의 이름은 도구마다 다르지만 넣는 값은 같습니다.

설정 항목넣을 값
Base URL / Endpointhttp://localhost:11434/v1
API Key아무 값이나 (로컬은 검사하지 않습니다)
Modelqwen3:8b 등 ollama list에 보이는 이름
연결이 안 될 때 localhost 대신 127.0.0.1로 바꿔 보세요. 도커 안에서 돌리는 런타임이라면 host.docker.internal:11434입니다.

  • 분류 기준 — 확장자로 나눴다가, 용도로 나눴다가

하네스 조립 — 반복 가능한 작업 환경 만들기

네 개의 기둥을 하나씩 세우고, 마지막에 두 번 돌려 확인합니다.

하네스의 네 기둥

  • 1규약매 실행이 같은 전제에서 시작하게 한다. 규칙·금지·산출물 형식을 CLAUDE.md에 적는다.
  • 2역할수집·작성·검증을 서브에이전트로 나누고, 각자에게 필요한 권한만 준다.
  • 3절차매번 하는 일의 순서를 스킬로 적는다. 사람이 아니라 문서가 순서를 기억한다.
  • 4게이트통과 여부를 스크립트가 판정한다. 못 넘으면 산출물이 나가지 못한다.

오늘 만들 것

지정한 폴더를 읽어 정리 리포트 1편을 만드는 하네스입니다. 파일을 옮기거나 지우지 않고 읽기만 하므로 안전합니다. 완성하면 이런 모양이 됩니다.

tidy-harness/ ├── CLAUDE.md ← ① 규약 ├── .claude/ │ ├── agents/ │ │ ├── scanner.md ← ② 역할 (수집) │ │ └── writer.md ← ② 역할 (작성) │ └── skills/ │ └── tidy-report/ │ └── SKILL.md ← ③ 절차 ├── scripts/ │ └── check-report.mjs ← ④ 게이트 └── out/ ├── scan.json ← 수집 결과 └── report.md ← 최종 산출물
CLAUDE.md scanner.md writer.md SKILL.md check-report.mjs
Terminal
mkdir -p tidy-harness/.claude/agents
mkdir -p tidy-harness/.claude/skills/tidy-report
mkdir -p tidy-harness/scripts tidy-harness/out
cd tidy-harness
PowerShell
mkdir tidy-harness\.claude\agents -Force
mkdir tidy-harness\.claude\skills\tidy-report -Force
mkdir tidy-harness\scripts, tidy-harness\out -Force
cd tidy-harness

에이전트가 이 폴더에서 일할 때 매번 먼저 읽는 문서입니다. 여기 없는 규칙은 매 실행 사람이 다시 말해야 하고, 사람은 깜빡합니다.

CLAUDE.md
# 다운로드 폴더 정리 하네스

## 목적
지정한 폴더를 읽어 분류 리포트 1편을 `out/report.md`로 만든다.

## 절대 규칙
1. **파일을 이동·삭제·수정하지 않는다.** 읽기와 리포트 작성만 한다.
2. 산출물은 `out/` 아래에만 쓴다.
3. **추측을 적지 않는다.** 파일명·확장자·크기·수정일로 확인되는 것만 쓴다.
4. 개인정보로 보이는 파일명은 `(파일명 생략)`으로 적는다.
5. **검증을 통과하지 못한 리포트를 완료라고 보고하지 않는다.**
6. 게이트를 통과하려고 `scripts/check-report.mjs`를 고치지 않는다.

## 산출물 형식
`out/report.md`는 아래 네 섹션을 **이 순서 그대로** 포함한다.
- `## 요약` — `총 N개` 형식의 파일 수, 총 용량, 가장 오래된 파일의 수정일
- `## 분류` — 문서 / 이미지 / 영상 / 설치파일 / 압축 / 기타 (각 항목에 개수)
- `## 정리 후보` — 90일 이상 수정되지 않았거나 이름이 겹쳐 보이는 파일
- `## 확인 필요` — 판단이 서지 않는 파일

빈 섹션을 남기지 않는다. 해당 항목이 없으면 "없음"이라고 적는다.

## 검증
`node scripts/check-report.mjs` 가 통과해야 작업이 끝난 것이다.
규칙 5번과 6번을 눈여겨보세요 둘 다 에이전트가 빠져나가는 길을 막는 조항입니다. 검사에 걸리면 산출물을 고쳐야 하는데, 그보다 검사를 고치는 쪽이 쉽습니다. 사람도 그렇게 합니다. 그래서 미리 적어 둡니다.

한 에이전트가 수집과 작성을 다 하면 둘 다 대충 합니다. 폴더를 보면서 동시에 글을 쓰면, 눈에 띄는 파일 몇 개로 결론을 내고 나머지를 안 셉니다. 그래서 재료를 만드는 쪽과 글을 쓰는 쪽을 끊습니다.

.claude/agents/scanner.md
---
name: scanner
description: 대상 폴더의 파일 메타데이터를 수집해 out/scan.json으로 남긴다. 분류·판단·작성은 하지 않는다.
tools: Bash, Read, Write
---

너는 **수집만** 한다. 분류도, 추천도, 글도 쓰지 않는다.

1. 폴더의 파일을 name, ext, size(바이트), mtime(ISO 8601)으로 모은다.
2. 읽은 그대로 `out/scan.json`에 JSON 배열로 저장한다. 요약하지 않는다.
3. 하위 폴더는 1단계까지만 들어간다.

하지 말 것:
- 파일을 **열어서 내용을 읽지 않는다.** 메타데이터만 쓴다.
- 파일을 이동·삭제·수정하지 않는다.
- 분류하지 않는다. 그건 writer가 할 일이다.

끝낼 때 총 파일 수와 총 용량만 한 줄로 보고한다.
.claude/agents/writer.md
---
name: writer
description: out/scan.json만 재료로 CLAUDE.md가 정한 형식의 리포트를 쓴다. 파일 시스템을 다시 읽지 않는다.
tools: Read, Write
---

너는 `out/scan.json` **하나만** 재료로 쓴다. 폴더를 다시 읽지 않는다.

1. CLAUDE.md의 "산출물 형식" 네 섹션을 그 순서 그대로 만든다.
2. 숫자는 scan.json에서 직접 센 값만 적는다. 파일 수는 `총 N개` 형식으로 쓴다.
3. 분류 기준은 확장자다. 확장자로 갈리지 않으면 "확인 필요"에 넣는다.
4. 다 쓰면 `out/report.md`로 저장한다.

하지 말 것:
- **추측하지 않는다.** "아마", "~인 것 같다"를 쓰지 않는다. 게이트가 잡아낸다.
- scan.json에 없는 파일을 지어내지 않는다.
- 섹션을 비워 두지 않는다. 없으면 "없음"이라고 적는다.
tools 줄이 권한입니다 scanner에게는 파일을 훑을 Bash가 필요하지만, writer에게는 필요 없습니다. writer는 Read와 Write만 가집니다. 필요 없는 권한을 주지 않는 것이 사고를 막는 가장 싼 방법입니다.

규약은 무엇을이고, 스킬은 어떤 순서로입니다. 순서를 사람이 기억하면 사람이 바쁜 날 순서가 바뀝니다.

.claude/skills/tidy-report/SKILL.md
---
name: tidy-report

# 다운로드 폴더 정리 리포트

## Phase 0 — 중복 실행 게이트
`out/report.md`가 이미 있으면 덮어쓸지 사용자에게 묻는다.
답을 받지 못하면 아무것도 하지 않고 종료한다.

## Phase 1 — 수집
`scanner` 에이전트에게 대상 폴더를 주고 `out/scan.json`을 만들게 한다.
**직접 폴더를 읽지 않는다.**

## Phase 2 — 작성
`writer` 에이전트에게 `out/scan.json`만 주고 `out/report.md`를 쓰게 한다.
폴더를 다시 읽게 하지 않는다.

## Phase 3 — 검증
`node scripts/check-report.mjs` 를 실행한다.
- 종료코드 0: 끝. 리포트 경로를 알린다.
- 종료코드 1: 지적된 항목만 고쳐 Phase 2부터 다시 한다. **최대 2회.**
- 2회 뒤에도 실패하면 리포트를 남긴 채 중단하고, 실패했다고 보고한다.

## 절대 규칙
1. 검증을 통과하지 못한 리포트를 "완료"라고 보고하지 않는다.
2. 게이트를 통과시키려고 check-report.mjs를 고치지 않는다.
3. Phase를 건너뛰지 않는다.
재시도 횟수를 적어 두는 이유 상한이 없으면 에이전트는 통과할 때까지 무한히 고칩니다. 토큰도 시간도 거기서 샙니다. 2회까지 하고 실패를 보고하라고 적어 두면, 실패가 조용히 묻히지 않습니다.

앞의 셋은 전부 문서입니다. 문서는 에이전트가 요약해서 읽을 수 있고, 요약된 규칙은 지켜지지 않습니다. 그래서 기계로 잡을 수 있는 것은 기계가 잡습니다.

check-report.mjs를 받아 scripts/에 넣으세요. 이 스크립트가 보는 것은 네 가지입니다.

  • 필수 섹션 넷이 정해진 순서로 있는가
  • 빈 섹션이 없는가
  • 요약에 적힌 파일 수가 scan.json의 실제 개수와 맞는가
  • 금지된 추측 표현("아마", "것 같다"…)이 섞이지 않았는가

셋째 항목이 특히 중요합니다. 숫자는 에이전트가 가장 쉽게 지어내는 것이고, 사람은 가장 알아채기 어려운 것입니다.

게이트가 도는지 먼저 확인
node scripts/check-report.mjs
# → [gate] out/report.md 가 없다. 작성 단계가 끝나지 않았다.
#   아직 리포트가 없으니 이렇게 나오는 게 정상입니다.

이제 에이전트에게 길게 설명할 필요가 없습니다. 저장소가 이미 다 알고 있습니다.

에이전트에게
tidy-report 스킬로 내 다운로드 폴더를 정리해줘.

한 줄입니다. 나머지는 CLAUDE.md와 SKILL.md가 말해 줍니다. 끝나면 결과를 봅니다.

확인
node scripts/check-report.mjs
cat out/report.md
지우고 다시
mv out/report.md out/report-1.md
# 에이전트에게 같은 한 줄을 다시 지시한 뒤
node scripts/check-report.mjs
diff out/report-1.md out/report.md

두 리포트의 문장은 여전히 조금씩 다릅니다. 그건 못 없앱니다. 하지만 세션 2에서 봤던 것과는 결정적으로 달라진 게 있습니다.

  • 섹션 구성과 순서가 두 번 다 같습니다
  • 파일 수가 두 번 다 실제와 맞습니다
  • 추측 문장이 두 번 다 없습니다
  • 그리고 이 셋을 사람이 확인하지 않았습니다
하네스가 주는 것 매번 똑같은 글이 나오는 게 아닙니다. 매번 쓸 수 있는 산출물이 나오는 것입니다. 그 기준을 사람이 아니라 저장소가 들고 있고, 사람이 자리에 없어도 작동합니다.

왜 게이트를 코드로 옮겼는가

처음에는 문체 규칙을 전부 문서에만 적어 뒀습니다. 그런데 몇 달이 지나 발행분을 세어 보니 145편 중 117편의 제목이 똑같은 틀로 찍혀 나오고 있었습니다. 규칙은 분명히 "다양하게 쓰라"였는데, 한번 잘 통한 형태가 굳어 공식이 된 것입니다.

사람도 눈치채지 못했습니다. 하루에 한 편씩 보면 멀쩡해 보이거든요. 145편을 한꺼번에 세어야 보입니다. 그래서 기계로 잡을 수 있는 규칙은 기계가 잡도록 옮겼습니다. 이것이 오늘 ④ 게이트를 넷째가 아니라 필수로 넣은 이유입니다.

가져갈 교훈 하나 규칙을 문서에만 적어 두면 천천히, 눈에 띄지 않게 무너집니다. 무너지는 걸 알아채려면 한 건이 아니라 누적된 결과를 세어 봐야 하고, 그건 사람이 아니라 스크립트가 잘합니다.

다음 단계

내 업무로 옮기기

세션 1에서 정해 둔 내 업무의 그 작업을 떠올려 보세요. 옮기는 순서는 오늘과 같습니다.

  1. 산출물을 먼저 정한다. 무엇이 어디에 어떤 형식으로 나와야 하는지 CLAUDE.md에 적습니다. 이게 가장 어렵고 가장 중요합니다.
  2. 판정 기준을 한 줄이라도 코드로 만든다. 완벽하지 않아도 됩니다. 섹션이 있는지만 봐도 게이트입니다.
  3. 역할을 나눈다. 재료 만드는 쪽과 결론 쓰는 쪽을 끊는 것만으로 품질이 올라갑니다.
  4. 순서를 스킬로 적는다. 그래야 다음 주의 내가 설명을 다시 하지 않습니다.
  5. 두 번 돌려 본다. 두 번 통과하면 세 번째부터는 사람이 안 봐도 됩니다.
순서를 바꾸지 마세요 사람들은 대개 ③ 절차부터 씁니다. 순서를 적는 게 제일 쉬우니까요. 그런데 산출물과 판정 기준이 없으면 절차는 아무것도 보장하지 못합니다. ①과 ④를 먼저 세우세요.

자주 막히는 곳

에이전트가 CLAUDE.md를 안 읽는 것 같습니다
파일 위치를 확인하세요. 저장소 최상위에 있어야 합니다. 그리고 규약이 너무 길면 에이전트가 요약해서 읽습니다. 절대 규칙은 10개를 넘기지 말고, 길어지면 스킬 쪽으로 옮기세요.
게이트가 계속 실패하는데 에이전트가 완료라고 보고합니다
CLAUDE.md 절대 규칙 5번과 SKILL.md Phase 3이 들어갔는지 확인하세요. "검증을 통과하지 못한 산출물을 완료라고 보고하지 않는다"가 글로 적혀 있지 않으면 지켜지지 않습니다.
에이전트가 게이트 스크립트 자체를 고쳐 버렸습니다
실제로 흔한 일입니다. 그래서 규약에 "게이트를 통과하려고 검사를 고치지 않는다"를 넣어 둡니다. 더 확실하게는 게이트 파일을 에이전트의 쓰기 권한 밖에 두거나, 버전 관리로 변경을 눈에 띄게 만드세요.
로컬 모델이 너무 느려서 실습이 안 됩니다
더 작은 모델로 내려가세요(qwen3:4b). 세션 3의 핵심은 모델 성능이 아니라 구조라, 느린 모델로도 네 기둥을 다 세울 수 있습니다. 구조를 먼저 만들어 두면 모델은 나중에 갈아 끼우면 됩니다.
scan.json이 너무 커서 모델이 다 못 읽습니다
파일이 수천 개인 폴더라면 scanner가 확장자별 개수만 집계하도록 바꾸세요. 컨텍스트에 무엇을 넣을지 정하는 것도 하네스 설계의 일부입니다. 재료를 통째로 넘기지 않고 추려서 넘기는 게 비용과 품질 양쪽에 유리합니다.
