01 · 대상과 목표

누구를 위한 과정인가

AI 도구를 이미 써 봤지만, 결과가 들쭉날쭉해 결국 손으로 고치고 있는 사람을 전제로 설계했습니다. 모델을 더 잘 고르는 법이나 프롬프트를 더 잘 쓰는 법은 다루지 않습니다. 같은 일을 매번 같은 품질로 끝내는 작업 환경을 만드는 것이 이 과정의 전부입니다.

이 과정이 다루지 않는 것 프롬프트 엔지니어링 기법, 모델 성능 비교, 파인튜닝, RAG 파이프라인 구축. 이것들은 한 번의 결과를 좋게 하는 방법이고, 이 과정은 반복되는 결과를 고르게 하는 방법입니다.

수료 시 할 수 있는 것

  1. Claude Code를 자기 작업 폴더에서 띄우고, 그 폴더가 왜 권한 범위가 되는지 설명할 수 있다.
  2. 같은 지시가 왜 다른 결과를 내는지 설명하고, 원인을 '규약이 없음'으로 진단할 수 있다.
  3. CLAUDE.md에 산출물 형식과 금지 사항을 적어 에이전트의 행동 범위를 좁힐 수 있다.
  4. 서브에이전트로 역할을 나누고, tools:로 각자에게 필요한 권한만 줄 수 있다.
  5. 스킬로 작업 순서를 고정하고, 재시도 횟수와 실패 시 행동까지 적을 수 있다.
  6. 판정 기준을 검증 스크립트로 옮기고, 통과하지 못한 산출물이 나가지 못하게 막을 수 있다.
  7. 자기 업무의 반복 작업 하나를 골라 같은 구조로 옮기는 계획을 세울 수 있다.
설계 의도 목표 1~2는 진단, 3~6은 조립, 7은 이전(transfer)입니다. 많은 실습 과정이 3~6만 가르치고 끝나는데, 그러면 참가자는 "파일 몇 개 만드는 법"을 배우고 돌아갑니다. 2번(왜 필요한지를 몸으로 아는 것)과 7번(내 일로 가져가는 것)이 이 과정의 실제 가치입니다.

02 · 전체 흐름

왜 이 순서인가

세 세션은 문제 → 체험 → 해결로 이어집니다. 순서를 바꾸면 작동하지 않습니다.

  • 1북토크 — 문제에 이름 붙이기AI를 '쓰는 일'에서 '맡기는 일'로 넘어갈 때 무엇이 어려워지는지 언어를 갖습니다. 아직 실습은 없습니다.
  • 2Claude Code — 문제를 몸으로 겪기같은 지시를 두 번 줘서 결과가 갈리는 것을 직접 봅니다. 이 체험이 세션 3의 동기 전부입니다.
  • 3하네스 조립 — 문제 풀기규약·역할·절차·게이트를 세우고, 두 번 돌려 기준이 고정됐음을 확인합니다.
가장 흔한 설계 실수 세션 2를 "도구 설치 시간"으로 보고 줄이는 것입니다. 그러면 세션 3이 이유를 모르는 채 파일을 만드는 지루한 작업이 됩니다. 세션 2의 마지막 15분(두 번 실행하고 비교하기)은 어떤 경우에도 줄이지 마세요. 줄여야 한다면 세션 3의 ② 역할 단계를 미리 배포한 템플릿 복사로 대체하는 쪽이 낫습니다.

Session 2 · 하네스의 바닥

19:55~20:40 · 45분
목표Claude Code의 작동 방식과 권한 모델을 이해하고, 규약 없는 에이전트의 한계를 직접 겪는다.
5분채팅창과 무엇이 다른가 — 복사해 나르지 않는다는 것강의
10분작업 폴더에서 띄우기 + /permissions 확인실습
10분연습용 파일 생성 → "정리 리포트를 만들어줘" 첫 작업실습
15분/clear 후 같은 지시 재실행 → 두 결과 비교 · 공유실습
5분진단 — 무엇이 빠져 있었는가토의

통과 기준

  • 두 결과의 차이를 세 가지 이상 말할 수 있다
  • 그 차이의 원인을 "모델이 나빠서"가 아니라 "기준을 안 적어 줘서"로 설명한다
강사 노트 — 이 세션이 과정의 승부처입니다 마지막 15분을 절대 줄이지 마세요. 참가자가 자기 화면에서 두 결과가 다른 것을 직접 봐야 세션 3의 지루한 파일 작업을 끝까지 따라옵니다. 말로 설명하면 효과가 없습니다.

비교 결과를 3~4명에게 소리 내어 공유시키세요. 다른 사람도 똑같이 갈렸다는 걸 확인하는 순간, "내가 프롬프트를 못 써서"가 아니라 구조의 문제라는 인식이 생깁니다.

흔한 실패와 대응

두 번째 결과가 첫 번째와 거의 같게 나옵니다
/clear를 안 했거나 같은 세션에서 다시 물은 경우입니다. 앞의 대화가 사실상 규약 역할을 해 버린 것이죠. 이것 자체가 좋은 교보재입니다 — "맥락이 있으면 일관됩니다. 문제는 그 맥락이 대화가 끝나면 사라진다는 것이고, 세션 3에서는 그걸 파일로 남깁니다"로 연결하세요.
홈 디렉터리에서 띄워 엉뚱한 파일을 건드립니다
실습 전에 반드시 mkdir → cd → claude 순서를 함께 치게 하세요. 승인 창이 뜨면 경로를 읽는 습관도 이때 들입니다.
진도가 빨라 15분이 남습니다
세 번째 실행을 시키고, 이번에는 원하는 형식을 프롬프트에 길게 적어서 주게 하세요. 결과는 좋아지지만 그 설명을 매번 다시 써야 한다는 것을 체감하게 됩니다. 세션 3의 "그 설명을 저장소 안에 둔다"가 훨씬 잘 꽂힙니다.

Session 3 · 하네스 조립

20:50~21:50 · 60분

통과 기준

  • node scripts/check-report.mjs가 두 번 연속 종료코드 0으로 통과한다
  • 두 리포트의 문장은 다르지만 섹션 구성·파일 수·추측 표현 없음은 같다는 것을 확인한다
강사 노트 — ④를 반드시 시간 안에 넣으세요 ①②③만 하고 끝나면 참가자는 "문서 많이 쓰는 법"을 배운 것으로 끝납니다. 게이트가 거절했다가 통과하는 경험이 있어야 "기준을 코드로 옮긴다"는 말이 실감됩니다.

시간이 모자라면 ② 역할 단계를 미리 배포한 템플릿 복사로 대체하세요(12분 → 4분). ①과 ④는 직접 쓰게 해야 합니다. 그 둘이 이 과정의 핵심입니다.

흔한 실패와 대응

게이트가 계속 실패하는데 Claude가 "완료했습니다"라고 합니다
CLAUDE.md 절대 규칙 5번과 SKILL.md Phase 3이 빠진 경우입니다. 이것도 좋은 교보재입니다 — "검증을 통과하지 못한 산출물을 완료라고 보고하지 않는다"가 글로 적혀 있지 않으면 지켜지지 않는다는 것을 그 자리에서 보여 주세요.
Claude가 게이트 스크립트 자체를 고쳐 버립니다
실제로 자주 일어납니다. 규약 6번("게이트를 통과하려고 검사를 고치지 않는다")이 왜 필요한지 보여 줄 기회입니다. 시간이 있으면 git diff로 스크립트가 바뀐 것을 함께 확인하세요.
파일 경로를 틀려 서브에이전트·스킬이 호출되지 않습니다
가장 흔한 실수는 스킬의 폴더 한 겹입니다 — .claude/skills/tidy-report/SKILL.md이지 .claude/skills/tidy-report.md가 아닙니다. 화면 공유로 트리 구조를 한 번 띄워 두고 진행하세요.
