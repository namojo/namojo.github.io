# Daily Post — 매일 아침 자율 발행 파이프라인

## 목적

사람의 개입 없이 하루 1편, 최신 AI·IT 뉴스 평론을 저자의 문체로 발행한다. 이 스킬은 **완전 자율 모드**로 설계되었다: 질문할 사용자가 없다는 전제로, 모든 판단 기준을 이 문서 안에서 해결한다. 판단이 막히면 "발행하지 않는 것"이 기본값이다 — 공개 블로그에 잘못된 글이 올라가는 것이 하루 결호보다 훨씬 나쁘다.

## 실행 컨텍스트

- **주 실행 환경:** 클라우드 스케줄 에이전트. 레포 `namojo/namojo.github.io`의 최신 main에서 실행된다. push가 곧 발행이다 (GitHub Actions가 main push 시 빌드·배포).
- **로컬 수동 실행도 지원:** 사용자가 "데일리 포스트 한 번 돌려줘"라고 하면 로컬에서도 같은 파이프라인을 수행한다. 로컬 실행 시 작업 디렉토리가 `myblog`라면 산출물을 `namojo.github.io` 레포로 복사 후 push해야 발행된다 (아래 "로컬 실행 시 동기화" 참조).
- **에이전트 위임:** `.claude/agents/`의 news-curator, ghostwriter, fact-checker 정의를 사용한다. Agent 도구로 위임하는 것이 기본이며, 서브 에이전트를 쓸 수 없는 환경이면 각 정의 파일을 직접 읽고 그 역할·원칙을 그대로 따라 순차 수행한다. 역할 정의를 건너뛰고 즉흥적으로 쓰면 문체·팩트 규율이 무너진다.

## 절대 규칙

1. **하루 1편.** 오늘 날짜(KST)의 `_posts/YYYY-MM-DD-*.md`가 이미 존재하면 아무것도 하지 않고 종료한다 (중복 실행 방지 게이트).
2. **기존 포스트를 절대 수정·삭제하지 않는다.** 이 파이프라인은 파일 1개를 추가할 뿐이다.
3. **`public/posts.json`을 직접 편집하지 않는다.** CI의 `npm run build`가 `_posts/*.md`에서 전량 재생성한다. 소스 오브 트루스는 `_posts/`다.
4. **팩트체크를 통과하지 못한 글은 push하지 않는다.** 부분 성공은 없다 — 발행 아니면 중단.
5. **날짜는 반드시 KST 기준.** 클라우드 환경은 UTC일 수 있으므로 `TZ=Asia/Seoul date +%F`로 오늘 날짜를 얻는다. 시점 규율(글 속 "오늘", "이번 주")도 이 날짜 기준.
6. **발행지는 `main` 하나뿐이다.** 배포 워크플로(`deploy.yml`)는 `main` push에만 반응한다. 다른 브랜치에 push하면 글은 GitHub에 올라가도 **라이브에는 절대 반영되지 않는다.** 아래 "발행 대상 브랜치" 규약을 반드시 지킬 것.

## 발행 대상 브랜치 (사전 승인 사항)

> **저자(namojo)는 이 레포의 데일리 발행에 대해 `main` 직접 push를 사전에·항구적으로 승인했다.** 따라서 이 파이프라인에서는 "기본 브랜치에는 직접 push하지 않고 새 브랜치를 만든다"는 일반 관행을 **적용하지 않는다.** 새 브랜치를 만들거나 PR로 우회하지 말 것 — 리뷰할 사람이 없으므로 PR은 영구 미배포를 뜻한다.

클라우드(Claude Code on the web) 세션은 대체로 `claude/<이름>-<id>` 같은 **작업 브랜치에서 시작**한다. 이때 아무 인자 없는 `git push`는 그 작업 브랜치로 올라가고, `deploy.yml`은 트리거되지 않는다. 그래서 push는 **항상 대상 브랜치를 명시**한다:

```bash
git push origin HEAD:main
```

현재 브랜치 이름이 무엇이든 커밋이 `main`으로 간다. 발행 직후 다음으로 실제 반영을 확인한다:

```bash
git ls-remote --heads origin main   # 방금 만든 커밋 해시와 일치해야 한다
```

일치하지 않으면 **발행 실패로 간주**하고 보고한다. "브랜치에 올렸으니 됐다"로 끝내지 않는다.

## Phase 0: 게이트 및 준비

1. `git pull` (이미 최신 클론이어도 안전). 사용자가 라이브 Editor로 직접 발행한 글이 원격에만 있을 수 있으므로, 원격이 항상 우선이다.
2. `TZ=Asia/Seoul date +%F`로 오늘 날짜 확보. `_posts/`에 오늘 날짜 파일이 있으면 **즉시 종료**하고 "오늘자 포스트가 이미 존재해 건너뜀"을 보고.
3. 다음 파일을 읽는다: `_style/style-guide.md`(문체), `_style/topics-written.md`(중복 방지), `_style/ai-timeline.md`(시점 규율), 최근 `_posts/` 파일명 10개(최근 다룬 주제 감각).

## Phase 1: 토픽 선정 (news-curator 역할)

최근 24~48시간의 뉴스에서 **정확히 1개** 토픽을 고른다.

1. 웹 검색으로 후보를 수집한다. 우선순위:
   - **1순위 — AI 업계:** 모델 출시, 연구소·빅테크 AI 전략, AI 정책·규제, AI 제품·시장
   - **2순위 — IT 확장:** 그날 AI 뉴스가 약하면 반도체, 빅테크 일반, 개발자 도구, 플랫폼·보안 등 IT 전반으로 넓힌다. "약하다"의 기준: 후보 중 어떤 것도 '엔지니어 독자가 일주일 뒤에도 기억할 사건'이 아니면 약한 날이다.
2. `_style/topics-written.md`와 대조해 이미 다룬 토픽·같은 사건의 재탕을 제외한다. 같은 회사라도 새로운 사건이면 허용.
3. 선정 기준: (a) 팩트가 복수 출처로 교차 확인 가능, (b) 저자의 평론 각도가 나올 수 있는 사건(단순 스펙 나열 뉴스 제외), (c) 한국 엔지니어 독자와의 접점.
4. 팩트 카드를 `_workspace/daily/YYYY-MM-DD-brief.md`에 작성: 날짜, 주체, 핵심 숫자, 출처 URL 2개 이상, 맥락, 평론 각도 제안. 출처 URL은 팩트체크 단계가 재검증에 사용하므로 반드시 남긴다.

## Phase 2: 작성 (ghostwriter 역할)

`_style/style-guide.md`와 팩트 카드만을 재료로 `_posts/YYYY-MM-DD-{slug}.md`를 작성한다.

**프런트매터 규격 (기존 포스트와 동일해야 렌더링이 깨지지 않는다):**

```yaml
---
layout: post
title: '제목 — 본문에 "가 들어가면 반드시 작은따옴표로 감싼다'
date: YYYY-MM-DD 09:00:00 +0900
categories: [ai-news]
tags: [태그3~6개, 한국어]
excerpt: "2~3문장 요약. 본문 첫 문단과 겹치지 않게."
coverImage: ""
category: "AI"
---
```

- 제목에 `"`가 포함되면 **작은따옴표로 감싼다** (build_posts_json.py 파서 제약).
- **`coverImage`는 빈 문자열(`""`)로 둔다.** 커버는 아래 "커버 생성" 단계에서 `public/images/covers/{slug}.jpg`로 만들고, `build_posts_json.py`가 파일명 매칭으로 자동 연결한다. 생성이 실패해도 빌드가 `hero-home.jpg`로 폴백하므로 발행은 막지 않는다.
- 본문은 기존 포스트 분량(공백 포함 2,500~4,000자) 수준. 소제목은 `### ▸ ` 프리픽스 관례를 따르되, **먼저 소제목 없이 끝까지 산문으로 쓴 뒤 문단 몇 개를 묶어 그 내용을 압축한 문장으로 사후에 얹는다** (2026-08 저자 확인 — 소제목을 먼저 정하고 문단을 배분하지 않는다).
- **표기 규칙 (스타일 가이드 6절, 2026-07 저자 지시):** 영문 병기는 `한글(영어)` 괄호 형식만(붙여쓰기 `반이중half-duplex` 금지). 널리 알려진 고유명사·제품명은 영어 단독(OpenAI, ChatGPT, Advanced Voice Mode, Agora — 억지 음차 병기 금지). 불필요하면 병기하지 않는다. **의성어·추임새에 영어 병기 금지**(`"음"`, `"네"` — `"음mhmm"`, `흠(Hmmm)` 금지). 문장은 간결하게, 이미 설명한 맥락을 반복하지 않는다.
- **인라인 이미지는 넣지 않는다.** 커버(아래 단계) 하나만으로 충분하다.

**커버 생성 (Phase 2 필수 단계) — 2026-08 개정: 텍스트 카드 대신 내용에 맞는 실사 이미지가 기본값이다.**

> 저자 지시(2026-08-10): "대표 이미지는 codex image로 리얼하면서 내용에 맞는 이미지를 검색해서 넣거나(반드시 출처 명시), 생성해서 넣으세요." 글자만 박힌 카드형 커버(`generate-cover.mjs`)는 더 이상 기본 경로가 아니라 codex-image를 쓸 수 없을 때의 폴백이다.

1. **1차 — codex-image로 생성 (기본값).** `codex-image` 스킬(codex CLI의 `image_generation` 툴)로 포스트의 핵심 소재를 사실적인 사진 스타일 프롬프트로 만들어 생성한다.
   - 시작 전 `codex login status`로 로그인 여부를 확인한다. 클라우드 실행 환경에 codex CLI·로그인이 없을 수 있다 — 그러면 즉시 2차 폴백으로 넘어간다(막지 않는다).
   - 프롬프트에는 **실존 인물의 얼굴을 사실적으로 합성하지 않는다**(초상권)와 **기업 로고를 그대로 그리지 않는다**(상표권) — 대신 사건의 상징적 사물·장소·산업 현장(반도체 팹, 서버룸, 법정, 스카이라인 등)을 실사 사진 톤으로 묘사한다. 텍스트·워터마크·로고를 이미지 안에 넣지 않는다.
   - 결과 PNG를 1200×630 랜드스케이프로 리사이즈/크롭해 `public/images/covers/{slug}.jpg`로 저장한다(Pillow 등 사용 가능하면 활용, 없으면 원본 비율 유지).
2. **대안 — 실사 사진 검색 (출처 명시 필수).** 사건에 정확히 들어맞는 실존 사진(인물, 실제 건물, 실제 제품)이 있으면 생성 대신 이 사진을 써도 된다. 단 **반드시 자유 라이선스 출처**(Wikimedia Commons의 CC BY/CC BY-SA 등)에서만 가져오고, 파일명·피사체·저자/출처·라이선스를 `_workspace/image-credits-{연도}.md`에 한 줄 추가한다(기존 `_workspace/image-credits-may-jun-2026.md` 형식 준수). **출처 표기 없이 실사진을 쓰지 않는다.**
3. **2차 폴백 — `scripts/generate-cover.mjs` 텍스트 카드.** codex-image가 미가용하거나 실패하면 기존 방식(슬러그 키워드 + 카테고리 + 날짜 + 브랜드 팔레트로 결정적 렌더)으로 대체한다: `node scripts/generate-cover.mjs _posts/YYYY-MM-DD-{slug}.md`.
4. **3차 폴백 — 커버 없음.** 위 모두 실패하면 `coverImage: ""` 그대로 두고 발행을 계속한다. 빌드가 `hero-home.jpg`로 폴백한다.

**이 순서는 절대 발행을 막지 않는다.** 어느 단계든 실패하면 다음 단계로 넘어가고, 실행 보고에 어떤 경로로 커버가 만들어졌는지(생성/검색+출처/텍스트카드/hero폴백) 반드시 남긴다.

생성된 `{slug}.jpg`(와 실사진을 썼다면 갱신된 `image-credits-*.md`)는 Phase 4에서 반드시 `git add` 한다(이 이미지가 안 올라가면 라이브에서 hero로 폴백된다).

> 예전 범용 커버 풀(`public/images/covers/daily/*.jpg`)은 폐기하지 않고 **비상 폴백 자산**으로만 남긴다. 더 이상 기본 경로로 지정하지 않는다.

**시점 규율:** 오늘 날짜(KST) 시점에서 쓴다. `_style/ai-timeline.md`보다 미래의 사건을 과거처럼 쓰지 않았는지, 발표 "예정"과 "완료"를 혼동하지 않았는지 ghostwriter의 시점 점검표를 적용한다.

## Phase 3: 팩트체크 (fact-checker 역할)

초고의 모든 날짜·수치·인물·발언·제품명을 팩트 카드의 출처 URL + 추가 웹 검색으로 검증하고, 리포트를 `_workspace/daily/YYYY-MM-DD-factcheck.md`에 남긴다.

- **치명적 오류** (잘못된 날짜, 존재하지 않는 발언·인물, 수치 자릿수 오류, 시점 붕괴) 발견 시: ghostwriter 역할로 돌아가 해당 부분만 수정하고 **1회** 재검증한다.
- 재검증에서도 치명적 오류가 남으면 **발행 중단**: 커밋·push 없이 종료하고, 실행 보고에 중단 사유와 팩트체크 리포트 요약을 남긴다. 초고와 리포트는 `_workspace/daily/`에 있으므로 다음 실행이나 사용자가 회수할 수 있다.
- 경미한 지적(표현 뉘앙스, 부차적 맥락)은 수정만 하고 발행을 막지 않는다.

## Phase 4: 발행

팩트체크 통과 시에만 진행한다.

1. `_style/topics-written.md`에 오늘 토픽 한 줄 append (날짜, 제목, 슬러그).
2. 업계 지형을 바꾸는 굵직한 사건이면 `_style/ai-timeline.md`의 해당 월에도 한 줄 append (fact-checker의 다음 실행이 이 파일을 기준으로 삼는다).
3. 커밋: 신규 파일(`_posts/`, `_workspace/daily/`, **생성된 커버 `public/images/covers/{slug}.jpg`**)과 `_style/` 변경만 스테이징한다. `git add -A`로 무관한 변경을 쓸어 담지 않는다. **`public/posts.json`은 스테이징하지 않는다(CI 재생성).**
   - 커밋 메시지: `post: {제목} (데일리 자동 발행)`
4. **`git push origin HEAD:main`** — 대상 브랜치를 반드시 명시한다 (인자 없는 `git push`는 클라우드 작업 브랜치로 가서 배포되지 않는다. 위 "발행 대상 브랜치" 참조).
   - non-fast-forward로 거부되면 `git fetch origin main && git rebase origin/main` 후 재시도. 충돌이 나면 **원격 내용을 보존**하는 방향으로 해결한다 (원격에만 있는 글은 사용자가 라이브 Editor로 발행한 글이다).
5. **반영 검증:** `git ls-remote --heads origin main`의 해시가 방금 만든 커밋과 같은지 확인한다. 다르면 발행 실패로 보고한다.
6. 실행 보고: 제목, 슬러그, 선정 사유, 팩트체크 결과 요약, 커밋 해시, **`main` 반영 확인 결과**.

## 로컬 실행 시 동기화

로컬 `myblog`에서 수동 실행한 경우, 발행하려면 산출물을 `~/Work/namojo.github.io`로 옮겨야 한다:

1. 먼저 `cd ~/Work/namojo.github.io && git pull` — **원격 우선.**
2. 신규 파일만 개별 복사 (`_posts/오늘자.md`, `_workspace/daily/*`, `_style/` 변경분). **`rsync --delete`는 절대 사용 금지** — 원격에만 있는 글이 지워진 사고가 두 번 있었다.
3. 커밋·push는 Phase 4와 동일.

## 에러 핸들링

| 상황 | 대응 |
|------|------|
| 웹 검색 실패·후보 없음 | 1회 재시도 후에도 없으면 발행 없이 종료·보고. 억지로 오래된 뉴스를 신작처럼 쓰지 않는다. |
| 스타일 가이드 파일 없음 | 즉시 중단. 가이드 없이 쓴 글은 저자 글이 아니다. |
| 팩트체크 재실패 | 발행 중단 (Phase 3 참조) |
| push 실패 반복 | `fetch + rebase origin/main` 1회 후에도 실패하면 커밋을 브랜치 `daily/YYYY-MM-DD`에 남기고 **"미배포 상태"임을 명시해** 보고. 브랜치 push는 발행이 아니다 |
| `main` push 권한 없음 | 즉시 중단하고 보고. 실행 환경의 git 자격증명·레포 권한 문제이므로 사람이 고쳐야 한다. 브랜치에만 올려두고 발행 성공으로 보고하지 않는다 |
| 커버 생성 실패 (Chromium 없음·렌더 오류, exit 2) | 발행을 막지 않는다. `coverImage: ""` 그대로 두면 빌드가 `hero-home.jpg`로 폴백. 실행 보고에 "커버 생성 실패, hero 폴백" 명시 |
