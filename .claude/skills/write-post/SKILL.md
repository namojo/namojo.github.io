# Write Post — 저자 문체로 포스트 한 편 쓰기

## 전제

이 스킬을 실행하기 전, 반드시 다음이 준비되어 있어야 한다:
- `_style/style-guide.md` (문체 헌법)
- `_style/ai-timeline.md` (시점 규율 레퍼런스)
- `_workspace/topic-briefs.md` 또는 명시적 토픽/팩트 입력

준비 안 됨 → 상위 오케스트레이터에 보고.

## 작업 순서

### 1. 스타일 가이드 완독
`_style/style-guide.md`를 전부 읽는다. 5가지 도입부 템플릿과 금기 목록을 꼭 확인.

### 2. 토픽 카드 선택
사용자 지정 토픽이 있으면 해당 카드. 없으면 topic-briefs의 첫 항목부터 선택.

### 3. 발행일 결정

- 사용자 지정 > 토픽 발생 후 1~4주 뒤 (저자가 뉴스를 보고 생각을 정리해서 썼을 법한 시점)
- 같은 날짜에 이미 포스트가 있으면 ±3일 조정

### 3-1. 시점 우주 확정 (필수)

`_style/ai-timeline.md`를 열고, **발행일 이전 섹션까지만** 읽어서 "이 글에서 언급 가능한 사건 화이트리스트"를 메모한다. 이 화이트리스트 바깥의 사건·모델·수치를 언급하면 즉시 시점 규율 위반.

필요하다면 웹 검색으로 누락된 시점 정보를 보강하되, 보강 결과는 `_style/ai-timeline.md`에 먼저 추가한 뒤 인용한다.

### 4. 제목 생성

⚠⚠⚠ **2026-10-13 전면 교체.** 이 절은 예전에 **"콜론 구조: 부제 : 본제"를 저자 스타일로 지시하고 있었고, 그것이 드리프트의 발원지였다.** 저자 지시(2026-10-13): "제목이 매우 AI가 쓴 것처럼 불편하다." 실측하면 발행 145편 중 **117편**의 제목이 ` : ` 쌍둥이 평서문이었다. 스타일 가이드 **2-A절**이 절대 우선한다.

**금지:** ` : `로 두 평서문을 잇는 구조. 평서문 종결어미(`~습니다`·`~입니다`)로 끝나는 제목. 30자 초과. 본문의 결론·반전을 제목에서 먼저 말하는 것.

**저자의 실제 제목 세 유형 (돌려 쓴다):**
1. **기사 헤드라인형** — `주체, 사건` 꼴. 기본값에 가깝다. 예: `구글, 우주 데이터센터 첫 궤도 실험`
2. **개념 명사구형** — 그 글이 설명할 대상을 명사구로. 동사로 끝나지 않는다. 예: `에이전트가 자신을 에이전트라고 밝히는 표준`
3. **헤드라인 + 구어 질문형** — 사건을 적고 쉼표로 끊은 뒤 짧은 걱정을 붙인다. 예: `AI에이전트가 DNS를 이용해 탈출, 이러다 큰일날까?`

길이는 **20~30자**(저자 실제 제목은 13~26자). 카피라이터스러운 "~하는 법 10가지" 같은 제목은 여전히 금지.

※ 책의 꼭지 제목(`560만 달러의 진실 : 숫자는 틀리지 않았지만, 전부는 아니었다`)은 **책 관례이고 블로그에 적용하지 않는다.** 블로그는 2-A절을 따른다.

### 5. 구조 작성

**도입부 다양화 (2026-08-11 저자 지시):** 최근 발행된 `_posts/` 3편의 첫 문단을 확인한다. 2편 이상이 연도로 문장을 열었다면(예: "1981년, IBM이…"), 이번 글은 연도로 시작하지 않는 템플릿(B·C·E·F·G)을 쓴다. 템플릿 A를 연속 2회 넘겨 쓰지 않는다.

```
## [도입 3~5문단]
스타일 가이드의 7가지 템플릿 중 토픽에 맞는 것 선택(최근 글과 다른 템플릿).

## [사건 소개 1~2문단]
팩트 블록: 날짜, 주체, 수치, 발언.

## [본체 — 메커니즘 설명]  ⚠ 이 글에서 가장 긴 부분이다
"그래서 그게 어떻게 돌아가는가"를 독자가 이해하게 만든다. 본문 절반 이상.
독자에게 직접 말을 건다("여러분이 사용하는 진공보온병을 떠올려 보세요").
비판적 균형은 이 설명 위에 얹는다 — 설명을 대신하지 않는다.

## [출처 바깥의 사고 1문단]
사건의 2차 효과를 저자 머리로 한 번 밀어 본다.
조건: 예측이 아니라 가정임을 적고, 그 가정이 기대는 근거를 같이 댄다.

## [마무리 1~2문단]
담백한 걱정·기대형(스타일 가이드 9절 유형 8). `~네요`/`~싶습니다`/`~있죠`로 끝나는 짧은 혼잣말.
```

⚠ **2026-10-13 교체.** 위 틀은 예전에 **`### ▸` 소제목 3개를 고정으로 요구**하고 있었고, 그 소제목들이 "숫자는 틀리지 않았습니다 : 다만 입력 쪽 숫자일 뿐입니다" 같은 감사(監査) 문체를 떠받치는 골격이 됐다. 저자가 다시 쓴 네 편에는 **소제목이 0개**다.
- **2,500자 미만: 소제목을 넣지 않는다**(기본값). 2,500자 이상이어도 최대 2개.
- 넣는다면 사후에 얹고, 제목 규칙(` : ` 금지·평서문 종결 금지)이 그대로 적용된다.

### 6. posts.json 엔트리 구성

```json
{
  "id": "english-slug",
  "title": "한국어 제목",
  "excerpt": "도입부 요약 1~2문장",
  "content": "(마크다운 본문, 실제 줄바꿈 포함)",
  "coverImage": "https://images.unsplash.com/photo-xxxxx?ixlib=rb-4.0.3&auto=format&fit=crop&w=1000&q=80",
  "date": "Feb 20, 2024",
  "likes": 100~500 사이,
  "author": {"name": "조남호 (namojo)", "avatar": "/images/author-avatar.jpg"},
  "tags": ["태그1", "태그2", "태그3"],
  "category": "AI"
}
```

### 7. posts.json에 안전하게 추가

1. `public/posts.json`을 Read로 읽는다
2. 기존 배열에서 동일 id가 있는지 확인 (중복 방지)
3. 새 엔트리를 삽입: `about` 엔트리 직후, 그 뒤의 엔트리들과 날짜 내림차순 정렬
4. 전체 JSON을 Write로 저장 (들여쓰기 2칸, UTF-8, 한글은 escape하지 않음)
5. **기존 엔트리는 절대 수정·삭제하지 않음**

### 8. 체크리스트 (저장 전)

- [ ] 발행일이 현재 날짜(2026-04-23) 이전인가?
- [ ] **본문의 모든 연도·월·사건이 발행일 이전인가?** (`_style/ai-timeline.md`로 2차 확인)
- [ ] **발행일 시점에 존재하지 않던 모델·용어·약어·인물 발언을 쓰지 않았는가?**
- [ ] 사후 시점 표현("훗날", "결국", "돌이켜보면", "나중에 드러나듯")이 없는가?
- [ ] 스타일 가이드의 금기 목록 어기지 않았는가?
- [ ] 본문 길이가 **1,600~2,800자**인가? (⚠ 2026-10-13 하향 — 이전 "2,500자 이상" 기준이 루틴을 매 편 4,000자까지 취재 디테일로 채우게 만들었다)
- [ ] **제목이 스타일 가이드 2-A절을 지키는가?** (` : ` 없음, 평서문 종결 없음, 30자 이내)
- [ ] **소제목이 분량 기준에 맞는가?** (2,500자 미만이면 0개)
- [ ] **이 글을 읽고 독자가 오늘 처음 알게 되는 원리가 있는가?** 사건 서술만 남았으면 다시 짠다
- [ ] **굳어 버린 관용구가 없는가?** (`더 정확한 표현은`, `증명하는 것과 증명하지 않는 것`, `그럼에도, 우린 ~ 사이에서 갈등하게 됩니다`)
- [ ] **`현지시각`을 쓰지 않았고, 본문의 `OpenAI`를 `오픈AI`로 적었는가?**
- [ ] **`node scripts/lint-post.mjs <파일>`이 종료코드 0인가?** (마크다운 백업을 `_posts/`에 쓴 경우 필수. ERROR면 저장하지 않는다)
- [ ] 팩트(숫자·날짜)가 topic brief와 일치하는가?
- [ ] 구체적 수치는 웹 검증되어 있거나 "추정/수준/규모" 같은 완화 표현인가?
- [ ] 저자의 고유 각도(비유·비판·한국 맥락)가 들어갔는가?
- [ ] posts.json의 **기존 엔트리가 모두 그대로** 있는가? (수량 확인)
- [ ] 새 id가 기존 id와 중복되지 않는가?

### 9. 품질 검수 (저장 전 필수, 2026-08-11 저자 지시)

초고를 posts.json에 확정하기 전에 아래 4가지를 문장 단위로 재검토해 직접 고친다. 건너뛰지 않는다.

1. **오탈자·오기**: 오타, 어미 오기(예: "전했네는데"→"전했는데"), 자모 이중 입력, 숫자·날짜·고유명사 철자 재확인.
2. **조사·문장 호응**: 나열형 문장에서 짝을 이루는 성분의 조사 통일 (예: "프로세서에서는 인텔에서, 운영체제는…"→"프로세서는 인텔에서, 운영체제는…"). 주어-술어·연결어미 호응 확인.
3. **개념어·인용구 가독성**: 비교·대조되는 핵심 개념·구문은 작은따옴표(' ')로 묶어 직관성을 높인다 (예: '볼 수 있는가'에서 '돌릴 수 있는가'로).
4. **어휘 격조·톤앤매너**: 지나치게 가벼운 속어·구어체는 격조 있는 표현으로 순화한다 ("갈라 먹다"→"나누어 차지하다/과점하다", "먹은 쪽"→"실리를 챙긴 쪽/시장을 선점한 쪽", "남의 부품"→"외부 부품/타사의 부품" 등). 예시와 같은 결의 표현을 발견하면 같은 기준으로 고친다.

### 10. fact-checker 호출

초고 저장 후 반드시 fact-checker 에이전트를 호출하여 `_workspace/factcheck-{slug}.md` 리포트를 받는다. 리포트가 "수정 후 발행" 또는 "발행 보류"로 판정되면 해당 엔트리를 수정한 뒤 재호출.

## 출력

`public/posts.json` (신규 엔트리 1개가 추가된 전체 파일). 기존 엔트리는 모두 보존.

## ⚠ 설명의 깊이 (2026-10-19 저자 지시)

저자 지시: **"너무 어려운 주제를 너무 어렵게 풀었습니다."** 메커니즘 설명은 지식 과시가 아니라 독자가 그 판단을 스스로 내리게 하는 수단이다. 저장 전 아래를 확인한다 — 스타일 가이드 **2-B절**이 기준이다.

1. 설명이 끝났을 때 독자가 할 수 있게 되는 일을 한 문장으로 적을 수 있는가. 없으면 글을 다시 짠다.
2. 전문 용어가 세 개를 넘지 않는가. 쓰는 용어는 첫 등장에 한 줄로 풀었는가.
3. 단위·규격·모델명·벤치마크를 나열하지 않았는가.
4. "그래서 무엇을 하면 되는가"가 한 문단 들어 있는가.
5. 끝까지 읽을 이유를 세 번째 문단 안에 줬는가.

## ⚠ 글을 끌고 가는 방식 (2026-10-19 저자 개고 — 스타일 가이드 2-C절)

저장 전 확인한다.

1. 설명할 것이 셋 이상인데 **"첫째·둘째·셋째" 목록으로 끊지 않았는가.** 구체적인 상황 하나로 바꿨는가.
2. 장면 전환·질문을 **한 줄 단락**으로 세웠는가(설명 문단은 덩어리로).
3. 질문을 던지기 전에 **독자의 전제를 먼저 말해 줬는가.**
4. 질문 뒤에 **한 줄로 답하고** 사례로 풀었는가.
5. 낯선 개념을 **독자가 아는 기본형과 대조해** 설명했는가.
6. 본문에 남긴 숫자와 출처 기관명이 **전부 논지를 떠받치는 것인가.**
7. 2,800자를 넘겼다면 사유가 (a)구체 시나리오 (b)출처 바깥의 사고 (c)끝까지 민 자문자답 중 하나인가.
