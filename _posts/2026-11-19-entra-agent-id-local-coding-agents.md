마이크로소프트가 11월 17일 샌프란시스코에서 Ignite 2026을 열었습니다. 나흘짜리 행사라 발표가 쏟아졌는데, 그중 한 줄이 눈에 걸렸습니다. 직원 노트북에서 돌아가는 Claude Code와 GitHub Copilot CLI를 회사 디렉터리가 찾아내 신원을 붙여 준다는 것이었어요. 신원 체계 자체인 Entra Agent ID는 이미 정식 출시됐고, 거기에 로컬 에이전트를 끌어들이는 이번 부분이 프리뷰입니다. 지원 대상의 시작점이 저 둘이고요. 문서가 적은 목적은 이겁니다. 에이전트의 활동을 사람의 활동에서 떼어내고, 그 접근을 안전하게 만드는 것.

그런데 여기서 걸리는 게 하나 있습니다.

회사가 어떤 프로그램에 신원을 주는 절차는 원래 정해져 있습니다. 관리자가 디렉터리에 앱을 등록하고, 클라이언트 ID와 자격증명을 발급하고, 권한을 붙이고, 그 프로그램이 그걸 들고 다니면서 토큰을 받아 옵니다. 업계에서는 이렇게 만들어진 주체를 서비스 주체(service principal)라고 부르는데요. 순서가 중요합니다. 신원이 먼저 있고, 돌아갈 물건이 나중에 그걸 가져다 씁니다.

로컬 CLI 에이전트는 이 순서에 들어맞지 않습니다. 개발자가 자기 노트북에 그냥 설치했고, 등록한 사람이 없고, 디렉터리는 그게 존재한다는 사실조차 모릅니다. 없는 것에 어떻게 신원을 주죠?

순서를 뒤집었습니다. 발견이 먼저입니다.

Defender가 관리되는 Windows·macOS 단말에서 돌아가고 있는 에이전트를 찾아내 단말과 사용자에 묶고, Global Secure Access가 네트워크 쪽에서 그 에이전트가 어디로 나가는지를 봅니다. 발견 대상이 60종을 넘는다고 하는데, 목록에 에이전트만 있는 게 아닙니다. 그 에이전트가 설정해 둔 MCP 서버까지 함께 집계됩니다. 이미 돌아가고 있는 것을 먼저 찾아낸 다음, 사후에 신원을 발급하는 구조인 거죠.

그럼 그 신원은 어떻게 생겼을까요.

노트북에 올라가 있는 프로그램은 비밀을 지킬 수가 없습니다. 클라이언트 비밀이든 인증서든 파일로 존재하는 한, 그 노트북을 쓰는 사람이 열어 볼 수 있으니까요. 그래서 마이크로소프트는 비밀을 잘 숨기는 방법을 찾는 대신 아예 주지 않는 쪽을 택했습니다. 로컬 에이전트는 퍼블릭 클라이언트(public client)로 등록하고 PKCE를 붙인 인가 코드 흐름을 쓰라고, 클라이언트 비밀도 인증서도 연합 자격증명도 달지 말라고 문서에 못을 박아 뒀어요. 그리고 한 줄이 더 있습니다. 설치본마다 신원을 따로 만들지 말고 전부 같은 클라이언트 ID를 쓰라고요. 노트북 천 대에 Claude Code가 깔려 있어도 Agent ID는 하나라는 뜻입니다.

그래서 이 체계에서 신원이 갈리는 단위는 사람도 노트북도 아닙니다. 에이전트 종류예요. 대신 사람은 다른 자리에 남습니다. 로컬 에이전트는 브라우저를 열어 사용자를 로그인시키고 그 사람을 대신해 권한을 받아 오는 구조라서, 발급된 토큰에는 둘이 같이 들어갑니다. 호출한 클라이언트는 에이전트, 로그인한 주체는 사람. 지금 우리 로그에 "아무개가 호출했다"로만 남는 줄이, 앞으로는 "Claude Code가, 아무개를 대신해서"로 쪼개진다는 이야기입니다. 조건부 액세스 템플릿이 사람을 대신해 움직이는 에이전트와 사용자 없이 혼자 움직이는 자율 에이전트 두 갈래로 나뉘어 나온 것도 이 구분 위에 서 있습니다.

그래서 지금 확인해 둘 것은 뭘까요. 프리뷰 기능을 켜는 일이 아닙니다. 우선 오늘 쌓이고 있는 로그를 열어 보시면 됩니다. 사내 API 호출 기록에서 Claude Code가 한 일과 그 개발자가 손으로 한 일이 지금 구분이 되나요? 거의 모든 조직에서 답은 "안 된다"일 겁니다. 둘 다 같은 사람의 토큰으로 나갔으니까요. 마이크로소프트가 적은 목적 문구가 정확히 이 지점을 가리킵니다.

그다음은 네 가지입니다. 관리 단말에서 어떤 로컬 에이전트가 돌고 있는지 목록이 있는가. 그 에이전트들의 MCP 서버 설정이 어디를 가리키고 있는가. 에이전트가 쓰는 토큰이 사람 토큰인가 별도 주체인가. 그리고 그 에이전트를 책임지는 사람이 퇴사하면 신원은 누구에게 넘어가는가. 마지막 항목에는 담당자가 조직을 떠날 때 책임자를 자동으로 옮겨 주는 수명주기 워크플로가 따로 준비돼 있습니다. 주인 없는 에이전트가 남는 것을 막으려는 장치죠. 참고로 Defender의 런타임 보호는 Defender for Endpoint P2가 전제이고 Audit 모드와 Block 모드 중에 고르게 되어 있는데, 이쪽 발견 기능은 정식 출시입니다. 반면 Agent ID 자동 부여와 Global Secure Access의 네트워크 발견, Intune 통제는 아직 프리뷰예요. 오늘 켜서 쓰는 물건이 아니라, 지금 설계를 정해 둘 영역입니다.

개인적으로 더 눈이 가는 건 발견 목록에 MCP 서버가 같이 들어갔다는 대목입니다. 에이전트가 무엇을 할 수 있는지는 모델이 정하지 않습니다. 그 노트북의 설정 파일에 어떤 MCP 서버가 적혀 있느냐가 정하죠. 마이크로소프트가 MCP 서버 접근만 따로 통제하는 기능을 함께 프리뷰로 내놓은 것도 같은 판단으로 보입니다. 예측은 아니고 가정입니다만, 이렇게 되면 조직이 들여다봐야 하는 섀도 IT의 단위가 설치된 프로그램에서 설정 파일 한 줄로 내려갑니다. 승인받지 않은 앱을 찾는 것보다 훨씬 성가신 일이죠.

에이전트에 이름표를 붙이는 일이 이렇게 급하게 돌아간다는 건, 그만큼 많은 조직이 이름표 없이 먼저 쓰기 시작했다는 뜻이기도 하네요. 우리 회사 로그에는 지난 반년 치가 어떻게 남아 있을지, 한 번쯤 열어 봐야겠다 싶습니다.
